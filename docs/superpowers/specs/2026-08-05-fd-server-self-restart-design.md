# 서버 자기 재기동 — `plugin update` 만으로 서버와 DB 까지 따라오게 한다

- 항목: `fd-server-self-restart`
- 날짜: 2026-08-05
- 상태: 설계 승인됨. 구현 계획 대기

## 1. 문제

`plugin update` 는 **소스만** 갱신한다. 그 뒤 무엇이 자동으로 따라오고 무엇이 안 따라오는지가 지금은 이렇다.

| 무엇 | `plugin update` 만으로 | 왜 |
|---|---|---|
| 훅 | **된다** | `bin/fd` 런처가 소스 mtime 을 보고 다음 훅에서 다시 빌드한다 |
| MCP 도구 | 안 된다 | 세션 시작 때 한 번 exec 된다. Claude Code 재기동이 필요하다 |
| 조정 서버 | **안 된다** | 도는 프로세스가 교체된 아이노드를 물고 옛 코드를 계속 돈다 |
| DB 스키마 | **안 된다** | 증분은 서버가 DB 를 열 때만 적용된다 |

### 실측 (2026-08-05)

```
/proc/666697/exe -> /home/aaron/.local/state/flightdeck/bin/fd (deleted)
  프로세스 기동  Aug 4 18:20
  파일 mtime    Aug 5 08:27   vcs.revision = 그 시각의 main tip
```

파일은 **8분 전 최신으로 교체됐는데 프로세스는 14시간 전 코드를 돌고 있었다.**
같은 순간 이 머신의 세션 30건이 그 옛 서버에 붙어 있었고, 그 사실을 알린 것은 아무것도 없었다.

이 설계가 없애려는 것은 **"고쳐서 밀었는데 왜 그대로냐"** 라는 구간이다.

### 지금 막 생긴 전제

`782b46e` 로 `/healthz` 가 **도는 프로세스의 빌드 좌표**를 낸다. 이 설계에 필요했던 것은
의지가 아니라 그 감지기였다. 다만 이 설계는 그 좌표를 **트리거로 쓰지 않는다**(§3 참조) —
표시와 진단에만 쓴다.

## 2. 범위

### 하는 것

`fd serve` 프로세스가 **자기 실행 파일이 교체된 것**을 감지해 스스로 재기동한다.
사람 승인을 받지 않는다. 재기동한 프로세스가 DB 를 열면서 증분이 자연히 적용된다.

### 안 하는 것

- **docker 경로의 자기 갱신.** 컨테이너는 자기 이미지를 다시 만들 수 없다.
  `docker compose up -d --build` 는 사람 몫으로 남는다. **대신 그 한계를 `fd doctor` 가 말한다.**
- **롤백.** 죽은 프로세스는 자기를 되돌리지 못한다. 되돌림을 넣는 것은 supervisor 를
  새로 만드는 일이고, 이 저장소는 Tier A 에서 러너 0을 유지한다(설계 §2).
- **서버가 직접 빌드하기.** 빌드 사다리는 `bin/fd` 런처 한 자리에만 둔다(§3).
- **MCP·훅 프로세스의 자기 재기동.** 그 둘은 수명이 짧거나 Claude Code 가 주인이다.

## 3. 핵심 결정 넷

### ① 무인 자동이다 — 사람 승인을 안 받는다

재기동은 그 서버에 붙은 모든 세션의 연결을 끊는다. 그런데도 무인으로 가는 근거:

- 클라이언트에 **아웃박스와 멱등 키**가 이미 있다. 끊긴 쓰기는 오프라인 경로로 떨어졌다가 재생된다.
- 읽기는 재시도하면 된다. 캐시와 `StaleBanner` 가 그 구간을 이미 다룬다.
- 승인을 받게 하면 **아무도 안 누른다.** 41커밋이 밀리지 않고 쌓여 있던 것이 그 증거다.

### ② 감지 신호는 소스가 아니라 **자기 실행 파일**이다

서버는 빌드를 모른다. `os.Executable()` 자리의 `dev·inode·size·mtime` 을 기동 시 기억하고,
주기적으로 다시 재서 달라졌으면 교체로 본다.

**기동 시 기준값은 `/proc/self/exe` 에서 읽는다**(있으면). 그 자리는 **지금 도는 이미지**의
아이노드를 가리키고, 파일이 이미 교체된 뒤라면 경로를 stat 한 값과 다르다. 경로만 stat 하면
"이미 낡은 채로 시작한 서버"가 자기를 최신으로 기억해 영원히 트리거하지 않는다.
`/proc` 이 없는 유닉스에서는 경로 stat 으로 떨어지고, 그때 이 갈래를 못 본다는 사실을 로그에 남긴다.

`ExeID` 의 `dev·inode` 는 유닉스 고유다.

> **정정 (구현이 이 문단을 바꿨다).** 원래 여기에는 "이 파일 전체가 유닉스 빌드 태그 뒤에 있고,
> 비유닉스는 `selfwatch_other.go` 의 **no-op** 이 받는다"라고 적혀 있었다. 실제로 실린 것은 다르고,
> 그 차이는 의도적이다.
>
> **① 파일 전체에 태그를 안 붙인다.** `selfwatch.go` 는 태그가 없고(`ExeID`·`Same`·`Action`·`Decide`
> 와 감시기 본체가 여기 한 벌만 있다), 태그가 붙는 것은 `selfwatch_unix.go`·`selfwatch_other.go` 이며
> 그 안에는 진짜로 갈리는 셋(`exeIDOfPath`·`selfWatchSupported`·`execSelf`)만 있다.
> 파일 전체에 태그를 붙이면 구조체가 태그 양쪽에 두 벌이 되고, 필드 집합이 갈리는 순간
> **태그 없는 `_test.go` 가 다른 플랫폼에서만 컴파일에 실패한다.** 계획 실행 중 실제로 그렇게 깨졌고
> `GOOS=windows go vet ./cmd/fd/` 이 그것을 잡았다(`go build` 는 `_test.go` 를 건너뛰어 못 잡는다).
>
> **② 비유닉스는 no-op 이 아니라 오류다.** no-op 은 "쟀는데 안 바뀌었다"와 "못 쟀다"를 같은 값으로
> 접는다 — 그러면 감시기가 조용히 아무것도 안 하는 상태로 살고, 그것이 이 설계가 §13 에서 없애려는
> 침묵 그대로다. `execSelf` 에서는 더 나쁘다: 빈 성공을 돌려주면 호출부가 **드레인까지 마친 뒤**
> "재기동했다"로 읽고 서버는 내려간 채로 남는다. 그래서 셋 다 `errSelfWatchUnsupported` 를 감싼
> 오류를 내고, `newSelfWatcher` 는 그 사실을 `Watching=false` + 사유로 화면에 올린다.

**왜 소스 mtime + 자체 빌드가 아닌가**: 그러면 빌드 판정 사다리가 `bin/fd` 런처와 서버 두 벌이 된다.
이 저장소는 "같은 판정을 두 자리에 두면 한쪽만 고칠 때 조용히 어긋난다"를 세 번 겪었고
(`resolveBody` 3벌, `BeaconDir` 사다리, `schema.sql` 표 정의), `TestBeaconDirDelegatesToTheOneOwner`
가 그 이유로 서 있다. 부수 효과로 서버 머신에 Go 툴체인도 소스 트리도 요구하지 않게 된다.

**왜 `/healthz` 의 빌드 좌표가 트리거가 아닌가**: 그 좌표는 **없을 수 있다**. 플러그인 캐시에는
`.git` 이 없어서 거기서 빌드한 바이너리에는 VCS 스탬프가 안 붙는다(`fd-vcs-stamp-blind-to-worktree`).
좌표로 트리거하면 실제 사용자 환경에서 영원히 안 뜬다. `ExeID` 는 항상 있다.

### ③ `exec` 전에 자식 프로세스로 검증한다

`syscall.Exec` 는 프로세스 이미지를 갈아치운다. 새 바이너리가 못 뜨면 **서버가 그냥 사라지고**,
bare 경로에는 되살릴 감시자가 없다. 이것이 이 기능이 오늘보다 나빠질 수 있는 유일한 길이다.

그래서 `fd selfcheck --db <경로>` 를 자식으로 1회 돌린다. 보는 것은 셋뿐이다:

1. 바이너리가 실행되는가
2. 자기 빌드 좌표를 내는가 (`buildinfo.Self()`)
3. DB 증분 계획이 `MigrateReject` 가 **아닌가** — **적용하지 않는다**

### ④ ③이 강등도 막는다 — 규칙을 새로 안 만든다

옛 바이너리로 되돌아가면 DB 버전이 그 바이너리의 `SchemaVersion` 보다 높다.
`PlanMigration` 이 이미 그 경우를 거절로 낸다(`store.go`). `selfcheck` 가 그 거절을 보고
`exec` 를 막으므로 **서버는 살아 있는 새 판 그대로 남는다.**

## 4. 구조

| 자리 | 무엇 | 신규/변경 |
|---|---|---|
| `cmd/fd/selfwatch.go` | **태그 없음.** `ExeID` · `Same` · `Action` · `Decide` 순수 함수 + 감시기 본체 | 신규 |
| `cmd/fd/selfwatch_unix.go` | `//go:build unix` — `exeIDOfPath` · `selfWatchSupported` · `execSelf` | 신규 |
| `cmd/fd/selfwatch_other.go` | `//go:build !unix` — 같은 셋을 **오류로**(no-op 이 아니다. §②의 정정을 본다). `internal/window/proc_other.go` 가 선례 | 신규 |
| `cmd/fd/selfcheck.go` | `fd selfcheck --db` 서브명령 | 신규 |
| `internal/store/probe.go` | `ProbeMigration(path) (MigrationPlan, error)` — 읽기 전용 | 신규 |
| `cmd/fd/serve.go` | 감시기 기동 + 트리거 처리 | 변경 |
| `internal/api/handlers_meta.go` | `/healthz` 에 `self_update` | 변경 |
| `cmd/fd/render.go` | `fd doctor` 서버 절에 자동 갱신 축 | 변경 |
| `cmd/fd/main.go` | `selfcheck` 를 서브명령 표에 | 변경(한 줄) |

**도구 수는 안 는다.** `selfcheck` 는 MCP 도구가 아니라 CLI 서브명령이다. DESIGN §1 원칙 ②가
못박은 것은 `MCP 도구 6개 · 스킬 3개`이고, `serve`·`mcp`·`hook` 처럼 사람이 직접 안 부르는
축에 하나 더 붙는다.

### `ProbeMigration` 이 왜 따로 필요한가

`store.Open` 은 **열면서 적용한다.** 검증은 적용하면 안 된다 — 검증하다 증분이 붙어 버리면
그 뒤 `exec` 가 실패했을 때 옛 프로세스가 새 스키마 위에서 돌게 된다. 그래서 읽기 전용으로 열어
`hasVersionTable · dbVersion · objectCount` 만 읽고 순수 함수 `PlanMigration` 에 넘긴다.

## 5. 흐름

```
기동    self := ExeID(os.Executable())
        os.Executable 실패 → 감시기를 안 띄우고 사유를 로그에 남긴다(조용히 넘기지 않는다)

30초    now := ExeID(같은 경로)
  ├ 같다        → ActNothing
  ├ stat 실패   → ActNothing + 한 번만 로그. 교체가 아니라 삭제다. exec 할 대상이 없다
  ├ 실패한 판과 같다 → ActNothing. 같은 고장난 바이너리를 30초마다 다시 돌리지 않는다
  └ 다르다      → ActVerify

검증    exec.Command(경로, "selfcheck", "--db", <내 db>)   타임아웃 15초
  ├ exit 0  → ActExec
  └ 그 외   → ActRefuse. 그대로 산다. 이 ExeID 를 '실패한 판'으로 기억한다
                파일이 **또** 바뀌면(= 사람이 고쳤으면) 다시 시도한다

'실패한 판'은 **메모리에만 둔다.** 디스크에 남기지 않는다 — 서버가 재기동하면 잊고 다시
시도하는 쪽이 맞다. 그 재기동은 사람이 한 것이고, 사람이 개입한 뒤에도 옛 판정을
계속 들고 있으면 "고쳤는데 왜 안 올라가냐"가 된다. 대신 살아 있는 동안의 거절은
`/healthz` 에 남아 `fd doctor` 가 찍는다.

실행    ctx 취소 → api.Serve 가 srv.Shutdown 으로 드레인(≤10초, 이미 있다)
        → syscall.Exec(경로, os.Args, os.Environ())
```

> ★ 개정(2026-08-05) — **위 "드레인" 한 낱말은 0.9.0 까지 거짓이었다.** `api.Serve` 의
> `BaseContext` 가 서버 수명 ctx 를 그대로 냈으므로 인플라이트 요청 컨텍스트가 전부 그
> 자손이었고, ctx 취소 한 번에 도는 요청이 먼저 죽었다 — `srv.Shutdown` 은 **기다릴 대상이
> 이미 없는 상태로** 도착했다. 즉 Shutdown 을 부르면서 그것이 할 일을 먼저 없앤 배선이다.
> 그 사이 코드 주석은 그 절단을 "아웃박스 + 멱등키가 덮는다"로 정당화했는데 그 근거도 틀렸다
> (절단은 미도달이 아니라 서버가 답한 500 이라 아웃박스가 안 탄다). **이 문서와 계획은
> 처음부터 옳은 것을 적었고 구현만 어긋나 있었다** — 항목 `fd-serve-basecontext-cuts-inflight`
> 에서 참이 됐다. 지금은 종료가 두 단이다: 수명이 정해지지 않은 응답에 통지 → 유예
> (`api.ShutdownGrace`) 안에서 대기 → 넘긴 것만 절단 + ERROR.

`os.Args` 와 `os.Environ()` 을 **그대로** 넘긴다. 새 프로세스가 같은 `--addr`·`--db` 로 떠야 한다.
증분은 그 프로세스가 DB 를 열면서 적용된다 — 마이그레이션을 따로 부르지 않는다.

### 폴링 주기

30초. 근거가 있는 값은 아니다 — 갱신은 사람이 `plugin update` 를 누른 뒤에만 오고,
그때 30초 안에 따라오면 충분하다. `fd-live-window-baseline` 처럼 나중에 근거를 만들 수 있으면
그때 고친다. **지금은 근거 없는 상수임을 주석에 적는다.**

> ★ 개정(2026-08-05) — **값은 30초 그대로지만 위 문단의 전제가 반증됐다.** 항목
> `fd-selfwatch-interval-baseline` 이 쟀다: "30초 안에 따라오면 충분하다"가 통제하는 것은
> `plugin update` 반응 시간이 **아니다.** 실행 파일을 다시 만드는 것은 `bin/fd` 런처이고
> 그것은 새 세션이 부를 때 도는데, 그 상류 지연이 사슬을 지배해서 이 주기는 최악 사슬의
> 1% 미만이다 — **0으로 줄여도 사람이 체감하는 반응은 안 줄어든다.** 이 상수가 실제로
> 통제하는 것은 **스큐 창**(새 클라이언트가 옛 서버를 부르는 구간)이다.
> 그리고 실측이 준 것은 **평탄 구간(1s~120s)** 뿐이라 그 안의 값을 데이터가 못 가른다 —
> 없는 꺾임을 지어내지 않는다. 그래서 "근거 없는 상수임을 주석에 적는다"는 처방은
> **폐기됐다**: 지금 코드가 적는 것은 도착 분포와 평탄 구간이고, 붙드는 것은 값이 아니라
> `selfUpdateReactionBudget ≤ selfUpdateSkewCeiling` 이다(DESIGN §10 3차 실측).

## 6. 오류 처리

| 갈래 | 무엇을 하나 | 사람이 보는 곳 |
|---|---|---|
| `os.Executable` 실패 | 감시기를 안 띄운다 | 서버 로그 + `/healthz` 의 `self_update.reason` |
| 실행 파일 stat 실패 | 계속 산다. 한 번만 로그 | 서버 로그 |
| `selfcheck` 타임아웃·비0 | 계속 산다. 그 판을 기억 | **`fd doctor` 의 자동 갱신 축** |
| 증분 계획이 reject | 위와 같다. 사유에 계획의 `Reason` 을 그대로 싣는다 | 같음 |
| `syscall.Exec` 실패 | 리스너는 이미 닫혔다. 사유를 로그에 남기고 **비0으로 죽는다** | docker 는 restart 정책이 받는다. bare 는 사람 몫 |
| docker 컨테이너 | 감시기가 `ActNothing` 을 유지하고 그 사실을 낸다 | `fd doctor` — "이 서버는 컨테이너다. 자기 갱신을 안 한다" |

마지막 줄이 이 설계의 태도다. **덮지 못하는 경로를 침묵으로 두지 않는다**(DESIGN §13).

```json
  "from": "07e5df4…", "to": "1d044b2…",
  "outcome": "refused",               // refused | failed
  "detail": "selfcheck exit 1 — 증분 계획이 reject: …"
}
```

★ **`watching` 이 먼저다.** 감시기가 안 떴는데(비유닉스·`os.Executable` 실패·컨테이너)
`last_at` 이 비어 있으면 "아직 갱신이 없었다"로 읽힌다 — 그것은 "안 보고 있다"와 전혀 다르다.
`buildinfo.Coord` 의 `Known` 이 같은 규율이고, 그 규율을 안 지켜 빈칸이 찍힌 적이 있다.

**성공은 이 필드에 안 남는다.** 성공하면 프로세스가 갈아치워져 새 프로세스는 그 사실을 모른다.
남는 것은 `build` 좌표가 바뀐 것뿐이고, 그것으로 충분하다.

### `syscall.Exec` 실패의 잔여 위험

검증을 통과한 직후에 `exec` 자체가 실패할 확률은 낮다 — 방금 자식으로 띄워 본 파일이다.
그래도 0은 아니고, 그때는 리스너가 닫힌 뒤다. **되살리는 척하지 않는다.**
줄이는 방법은 검증과 `exec` 사이의 창을 좁게 유지하는 것뿐이고, 그래서 검증은
드레인 **직전에** 한다(미리 해 두고 나중에 쓰지 않는다).

## 7. 시험

핵심은 **감시기가 "무엇을 할지"를 순수 함수로 정하고, `syscall.Exec` 를 주입받는 것**이다.
그래야 시험이 "이 경로·이 인자로 exec 하려 했다"를 프로세스를 안 죽이고 단언한다.

```go
type Action int   // ActNothing · ActVerify · ActExec · ActRefuse
func Decide(start, now ExeID, lastFailed ExeID, statErr error) (Action, string)  // 순수
```

| 무엇 | 어떻게 | 종류 |
|---|---|---|
| `Replaced` · `Decide` | 표 구동 — 같음 · inode 다름 · mtime 만 다름 · stat 실패 · **실패한 판과 같음** · 실패 뒤 또 바뀜 | 순수 |
| `ProbeMigration` | 임시 DB 를 상태별로 — 빈 DB · 정상 · 버전 표만 있음 · 버전 표 없는데 객체 있음 · **DB 버전 > 코드 버전** | 실물 DB |
| `fd selfcheck` 종료코드 | 서브명령을 in-process 로(기존 `cmd/fd` 하네스 관용구) | 통합 |
| `/healthz` 의 `self_update` | `HealthzOf` — 시도 없음 · 성공 · 거절 | 순수 |
| `fd doctor` 출력 | `RenderHealth` — **거절이 화면에 뜨는지** | 순수 |
| exec 호출 | 주입된 스텁으로 경로·인자·환경을 단언 | 순수화된 통합 |

### 시험하지 않는 것

- **진짜 `syscall.Exec`.** 프로세스를 갈아치우는 것을 시험 안에서 할 수 없다.
  실물로 한 번 확인하고 그 관측을 판단에 남긴다.
- **다른 머신의 서버.** 이 축은 서버마다 독립이지만 그 독립성을 시험이 확인하지는 않는다.
- **docker 경로의 갱신.** 설계가 안 덮는다. 덮는 것은 그 사실을 화면에 내는 것까지다.

## 8. 이 설계가 답하지 않는 것

`plugin update` + Claude Code 재기동 뒤에도 **MCP 도구는 여전히 재기동이 필요하다.**
이 설계는 서버와 DB 축만 없앤다. MCP 는 Claude Code 가 프로세스의 주인이라
플러그인이 자기를 다시 띄울 수 없다 — 별개 항목이다.

그리고 **세션이 다른 머신에 있으면** 그 세션은 서버 갱신에 아무 영향을 못 준다.
이 설계에서는 그것이 문제가 아니다 — 서버가 자기를 갱신하므로 누가 붙어 있든 상관없다.
다만 **서버 머신에 Claude Code 세션이 하나도 안 도는 전용 서버**는 런처가 안 돌아
바이너리 자체가 갱신되지 않는다. 그 경우는 docker 경로이고, 위와 같이 사람 몫이다.
