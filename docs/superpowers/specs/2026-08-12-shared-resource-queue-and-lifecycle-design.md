# 공유자원 줄서기 일반화 + 대기 세션 자동 재개 + 세션 라이프사이클 관문 — 설계

작성 2026-08-12 · 상태 **초안**(브레인스토밍 2026-08-12) · 항목 `fd-shared-resource-queue-and-lifecycle-gates`

선행: `docs/superpowers/specs/2026-08-05-landing-order-queue-design.md`(랜딩 줄의 원설계 — 이 문서는 그것을 일반화한다)

## 문제

사용자가 관측한 것 셋:

1. 공유자원(랜딩·배포서버)을 남이 쥐고 있으면 **세션이 그냥 멈춰서 다음 지시를 기다린다.**
2. 여러 세션이 동시에 대기하면 **무한대기하거나 머지가 꼬인다.**
3. `pick` 으로 시작한 작업이 후속만 남기고 끝나며, `finish`·핸드오프·랜딩까지 가는 규율이 없다.

조사(12에이전트 전수 + 적대적 반증)가 이 셋의 기구를 각각 특정했다.

### ① 멈추는 기구 — 처방은 push 가 아니라 pull 이다

랜딩 줄은 **이미 있다.** `landing_queue` 가 FIFO 큐이고(`id` 가 순번), 순서 집행 지점은
`front.ID == mine.ID` 비교 하나다(`service/landing.go:136`, 주석은 `:106-107`).
차례 통지도 있다 — `lane-turn:<줄 행>` 처방이다.

**그런데 처방은 Stop 훅이 턴 끝에 끌어가는 pull 이다**(`cmd/fd/hook.go:557` 의
`a.cli.Write(ctx, CmdPrescriptions, …)`). 대기 세션이 "너는 2번째"를 듣고 턴을 끝내면
**다음 턴이 없다.** 앞사람이 레인을 놓아 `lane-turn` 이 떠도 그것을 끌어갈 턴이 영영 안 온다 —
사람이 무언가 칠 때까지.

실측이 이것을 뒷받침한다: **원장에 `lane-turn` 처방은 전 기간 0건이다**
(`judge/prescribe.go:73-77` — `kind='prescribe'` 257건 시점의 축 분포는
overlap 138 · unclaimed 67 · silent 37 · outside 15).
차례 통지 축의 실효는 이 저장소에서 **한 번도 실측된 적이 없다.**

### ② 자원이 랜딩 하나뿐이다

`LaneResource = "landing"` 은 상수 하나로 고정이고(`service/landing.go:34`), 프로덕션
하드코딩 호출부가 **10곳**이다(`service/landing.go:137·233·256·308·311·370·577·584·650` +
`service/prescribe.go:393`). `landing_queue` 를 읽고 쓰는 프로덕션 SQL 9문 중
**resource 술어를 가진 것은 0건**이다.

배포서버처럼 "한 번에 한 세션"인 다른 자원은 `resource_hold` 로 배타만 되고 **줄이 없다** —
경합하면 거절이고, 거절된 세션이 다시 설 자리가 없다.

### ③ 라이프사이클의 순서가 하나도 강제되지 않는다

전수 결과: **단계 사이의 순서를 묻는 코드가 사실상 없다.**

| 건너뛰기 | 지금 |
|---|---|
| `pick` 없이 `finish` | **통과한다.** `Tx.FinishItem` 의 switch 3갈래에 "선점 행이 없다"가 없어 그대로 `SetItemState` 로 떨어진다(`store/item.go:983-1004`). 시험이 그 통과를 직접 단정한다(`store/store_test.go:730-733`) |
| `land` 없이 `finish` | **통과한다.** 오히려 `finish` 가 그 세션의 줄 행을 `left_kind='finish'` 로 대신 닫는다(`service/finish.go:520-526`) |
| `finish` 없이 세션 사망 | **아무 일도 안 일어난다.** SessionEnd 훅은 matcher 가 `clear` 하나뿐이라(`hooks/hooks.json:64`) 창 닫기·kill 을 못 잡고, 잡아도 선점을 든 카드는 일부러 안 닫는다(`hook.go:650-654`). `claim` 표에 만료 컬럼도 자동 반납도 없어 **사람이 회수할 때까지 영구히 잠긴다** |

★ 전칭으로 "0건"이라 적으면 거짓이다 — `finish_followups.go:132` 의 `GetClaim` 이 정확히
"이 항목을 언제 선점했나"를 묻고, `followups` 에 잇기가 실려 있으면 자격 판정 실패로
**거절한다**(`finish_followups.go:337·385`, 관문 `GateFollowupIneligible`).
즉 잇기가 있는 경우에 한해 앞 단계를 묻는 자리가 하나 있다.

그리고 **`land` 를 언제 부르는지 말하는 표면이 0건이다.** MCP `instructions` 3줄에
`land` 라는 낱말이 없고(`mcpsrv/protocol.go:26-28`), 스킬 넷에도 레인 규율이 없다.
①의 "lane-turn 0건"은 통지 축이 고장난 것이 아니라 **아무도 줄에 안 섰기 때문**일 수 있다 —
줄에 서야 뜨는 처방이다.

## 조사에서 나온 제약 — 설계를 실제로 바꾼 것들

처음 세운 설계안 다섯 중 **넷이 반증으로 깨졌다.** 원안을 지우지 않고 무엇이 왜 틀렸는지 적는다.

### 제약 1 — SSE 로는 대기할 수 없다 (원안 ② 폐기)

원안은 기존 SSE(`/api/v1/events`)를 구독해 `lane.*` 프레임이 올 때만 재조회하는 것이었다.
네 겹으로 깨진다:

| 축 | 사실 |
|---|---|
| 클라이언트 | `cmd/fd` 프로덕션 코드에 SSE 를 읽는 코드가 **0건**이다. `Client.do` 는 `io.ReadAll(io.LimitReader(resp.Body, 16<<20))`(`client.go:224`)에 HTTP 타임아웃 기본 5초(`client.go:162-167`)라 끝나지 않는 스트림에 원리적으로 못 붙는다 |
| 관문 | `Client` 우회(`a.cli.do` 직접 호출)는 AST 관문이 그 자리에서 빨갛게 만든다 — 정당화와 함께 `knownCliDoWrites` 에 올려야만 통과하고 지금 셋뿐이다(`write_cmd_table_coverage_test.go:327-354·498-548`) |
| 와이어 | **`lane.*` 프레임에 자원 축이 없다.** detail 은 `{row,state,count}`(`handlers_landing.go:103-105`)와 `{row,held_release,actor}`(`:152-154`) 둘뿐이고 허브 필터는 project 하나다(`api/sse.go:141`). "그 자원의 프레임"이라는 구분이 오늘 와이어에 존재하지 않는다 |
| 결정타 | **가장 흔한 반납 경로인 `finish` 는 `lane.*` 를 아예 안 낸다** — `item.finish` 로 나간다(`handlers_items.go:253`). 그런데 `Finish` 는 자원을 반납하고 줄 행도 닫는다(`finish.go:461-526`). `lane.*` 만 듣는 대기자는 **이 반납을 통째로 못 듣는다** |

부수로: SSE 는 이 저장소가 명시로 "최적화이지 정본이 아니다"라 판정한 통로이고(`api/sse.go:13-16`),
구독자가 느리면 프레임을 버리며(버퍼 32, `:144-148`), 서버 드레인이 스트림을 끊는다
(`handlers_meta.go:418-428`).

**→ 읽기 전용 조회 + 백오프 폴링으로 간다.**

### 제약 2 — Stop 훅 block 은 카드 갈림에 걸린다 (원안 ③ 수정)

훅 stdout 계약 구조체에 `decision` 필드가 **아예 없다** — 지금 낼 수 있는 것은
`hookSpecificOutput.{hookEventName, additionalContext}` 둘뿐이고(`hook.go:92-101`),
Claude Code 훅 계약의 다른 통제 필드(`decision`/`continue`/`stopReason`/`suppressOutput`/
`systemMessage`/`permissionDecision`)는 이 저장소 전체에 0건이다. 필드를 더하는 것 자체는 가능하다.

**진짜 문제는 판정이 헛돈다는 것이다.** 처방·훅은 **발자국 카드**에서 뜨고 `land` 는
**MCP 판단 카드**로 온다(`DESIGN.md:1645-1650`). 두 카드가 갈린 대화에서는 훅 카드에
살아 있는 줄 행이 없으므로 **"줄 행은 있는데 레인을 안 쥐었다"가 정확히 필요한 순간에
거짓이 된다.** 이것은 실측된 미해결 결함이고 "통로를 뚫었다고 사라지지 않는다"고 적혀 있다.

★ **우회로가 같은 파일에 있다.** `AckReach`(`board.go`)는 2026-08-08부터 키를 안 보고
**대화 단위**(machine + cc_session_id)로 센다 — 카드가 갈려도 한 번 센다
(`service/prescribe.go:446-450`). 라이프사이클 판정을 그 단위로 하면 카드 갈림을 통과한다.

그리고 반증이 든 두 번째 지적 — "억제표는 이미 명시로 기각된 방벽이고
(`hook.go:525-533`), 억제가 작동하면 block 은 1회뿐이라 지속을 못 만든다" — 는
**원안이 억제표를 루프 방벽으로 쓴 탓이다.** 이 설계는 그것을 안 쓴다(아래 §4).

### 제약 3 — 성공 응답 산문은 준수 8% 다 (원안 ⑤ 폐기)

> "거절-시점 안내는 이 저장소에서 준수가 실측된 유일한 표면 부류다
> (관측 전 사례 준수 vs **성공 응답 산문 8%**)." — `service/finish_followups.go:99-102`

그 8% 의 실패 사례가 `land` 와 같은 모양으로 이미 적혀 있다:

> "지금도 응답 꼬리에 '후속 0건' 이 나가는데, 그 줄은 **성공 응답에 섞여** 나가서 안 읽힌다.
> 이 항목 자체가 그 실패의 산물이다 — 그 줄을 보고도 넘어간 세션이 이 관문을 만들고 있다."
> — `finish_followups.go:73-75`

`RenderLand` 는 `isError=false` 인 성공 응답으로 나가고(`mcpsrv.go:950`), 이미 폴링·처방
규율을 나르려고 두 문장을 쓰고 있다(`render.go:1878-1889`). 원안 ⑤("새 스킬 안 만들고
`land` 응답 문구가 규율을 나른다")는 **이미 8%인 자리에 부하를 더 얹는 것**이다.

**→ 규율을 항상 읽히는 자리(MCP `instructions`)와 거절 문구로 옮긴다.**

### 제약 4 — 자원 축은 SQL 7문과 하드코딩 10곳을 전부 가른다 (원안 ① 수정)

원안은 "`landing_queue` 에 `resource` 컬럼을 더하되 유니크 인덱스는 그대로 두면 데드락이
**스키마로** 불가능해진다"였다. 두 군데가 틀렸다.

**첫째, 스키마가 보장하는 것은 "세션당 살아 있는 줄 행 ≤1"뿐이다.** 데드락 부재의 전제인
"살아 있는 점유에는 반드시 살아 있는 줄 행이 있다"는 service 코드가 지키는 불변식이고,
저장소는 그것이 깨진 상태에 이미 이름을 붙여 놓았다 — `lane.divergent`
(`service/landing.go:21-26·247-251`). 데드락 부재는 스키마가 아니라 **그 불변식**이 만든다.

**둘째, 컬럼만 더하면 다음 넷이 조용히 틀린다.** 전부 `project` 만 본다:

| 자리 | 지금 | 자원이 섞이면 |
|---|---|---|
| `frontLandingRow` (`store/landing.go:191-204`) | `WHERE project=? AND left_at IS NULL ORDER BY id LIMIT 1` | 자원 A 의 오래된 대기자가 **프로젝트의 모든 자원**을 막는다 |
| `EnqueueLanding` 재진입 (`store/landing.go:104-110`) | 유니크 위반이면 `liveLandingRow(project,session)` 을 성공으로 반환 | **다른 자원의 줄 행**을 그대로 내준다 |
| `lanePosition` (`service/landing.go:637-648`) | project 전체 줄에서 `pos = i+1` | 자원 B 의 첫 대기자가 "4번째"로 답해진다 |
| `laneTurnRow` (`service/prescribe.go:379-402`) | `FrontLandingRow(project)` × `HeldBy(project,"landing")` | 자원 B 줄 맨 앞에게 "네 차례다"를 낸다 |

그리고 `ReleaseLaneRow` 는 **줄 행 번호**로 회수하면서 점유는 언제나 `'landing'` 을 본다
(`landing.go:577·584`) — 자원 B 의 줄 행을 회수하며 landing 점유를 강제 반납할 수 있다.
회수 판단 본문도 project 전체 줄을 "그때 줄에 있던 사람"으로 적어(`landing.go:713-717`)
불변 기록에 다른 자원의 대기자가 박힌다 — 같은 파일 `:525-527` 이 명시로 금지하는 부류다.

### 제약 5 — 요구 하나는 이미 구현돼 있다

"남은 큐 건수와 R 을 마무리 때 출력"은 **오늘 거동 그대로다.**

- R 은 `render.go:1669` 가 `최근 %d회 마무리 기준 R=%.2f — %s` 로 무조건 찍는다.
  찍는 자리는 전 저장소에서 그 한 곳이고 호출자는 `RenderFinish` 하나다.
- 큐 건수는 `render.go:978/980` 이 `큐 열림 %d건` 으로 낸다.

다만 두 가지가 요구와 다르다:

1. **R 은 프로젝트 단위다.** 두 질의 어디에도 `session_id` 필터가 없다
   (`store/event.go:388-390·436-437`). 창은 "그 프로젝트의 최근 20개 `item.finish`" 라
   다른 세션의 마무리가 전부 섞인다. "이번 세션의 R"을 내는 표면은 0건이고, 만들어도
   세션당 finish 표본이 1~2건이라 통계가 안 된다. **세션 몫으로 이미 있는 값은
   `Delta()`("이 마무리가 닫음 %d · 만듦 %d → %+d", `render.go:1631`)다.**
2. 금지된 것은 숫자도 추세 문구도 아니라 **R≥1 을 발화 조건으로 삼는 행동 요구**다
   (`render.go:1480-1483` — "전 관측창에서 상시 참이라 판별력이 0이고, 지표 도입 당일
   필요한 후속을 회피한 굿하트 실물이 이미 있다"). 그 자리는 "창작 후속 ≥3(버스트)"으로
   이미 대체됐다.

**→ 이 축에서 새로 만드는 것은 없다. 지키고 손대지 않는다.**
(다만 그 판정을 무는 시험이 0건이라 주석 한 줄이 유일한 방벽인 것은 아래 §8 에서 닫는다.)

## 확정한 결정

| 축 | 결정 | 사유 |
|---|---|---|
| 자원 모델 | 줄 행 하나가 **자원 집합**을 갖는다(새 표) | 경로를 자원으로 쓰면 한 작업이 파일 여럿을 요구한다. 자원마다 줄 행을 따로 두면 순환대기가 살아난다 |
| 취득 | **all-or-nothing** — 모든 자원에서 내가 최선두이고 전부 비었을 때만 전부 잡는다 | 부분 취득은 그 자체가 데드락의 재료다 |
| 세션당 줄 행 | 1개(기존 부분 유니크 인덱스 그대로) | 순환대기가 불가능해지는 자리. 인덱스를 **안 건드리는 것**이 이 설계의 선택이다 |
| 자원 이름 | 임의 문자열 `[A-Za-z0-9._/:-]`, 1~200자. 첫 취득이 이름을 만든다 | 고정 목록도 `.flightdeck.yaml` 로더도 안 만든다(원설계가 이미 기각). `:` 를 허용하는 것은 `path:<경로>` 규약 때문이고, 경로가 들어오므로 `/`·`.` 도 필요하다. 상한 200 은 오류 문구가 `clip(resource, 64)` 로 자르는 기존 관례(`store/resource.go:94`)보다 넉넉하되 무한하지 않게 두는 값이다 |
| 순서 | FIFO(`landing_queue.id`) 유지. 우선순위 축 없음 | 값을 누가 정하는지가 새 판정이 되고, 자기 값을 올리면 굶주림이 생긴다 |
| 굶주림 | 각 자원의 최선두는 뒤로 안 밀린다 | 보수적 2단계 잠금의 큐 형태. 여러 자원을 요구해도 결국 전부 모인다 |
| 대기 통로 | **읽기 전용 조회 + 백오프 폴링** | 제약 1 |
| 대기 프로세스 | `fd lane wait` 한 모양. `--background` 안 만든다 | fd 를 데몬화하면 수명·정리가 새 문제가 된다. 백그라운드는 부르는 쪽(하네스 `run_in_background`)이 이미 갖고 있다 |
| 죽은 선두 | **에스컬레이션.** 자동 회수 없음 | `store/resource.go:14-19` 의 규율. 생존 오판 실측 2건 |
| 라이프사이클 강제 | Stop 훅 `decision:"block"`, 판정은 **대화 단위** | 제약 2 |

| R·큐 건수 | **새로 안 만든다** | 제약 5 |

## 설계

### 1. 데이터 모델 — 표를 더하고 기존 표는 안 건드린다

★ `schema.sql` 을 고치지 않는다. 증분은 `internal/store/migrations/NNN_*.sql` 이다.
현재 최신 증분은 **007** 이고 `SchemaVersion = 7`(`store/store.go:55`, migrations 목록 `:76-83`)이므로
새 파일은 **`008_resource_queue.sql`** 이고 상수를 **8** 로 올린다.

```sql
-- 008 · 줄 행이 자원 집합을 갖는다 (schema_version 7 → 8)

CREATE TABLE landing_queue_resource (
  row_id   INTEGER NOT NULL REFERENCES landing_queue(id),
  resource TEXT NOT NULL,
  PRIMARY KEY (row_id, resource),
  CHECK (resource <> '')
);

-- 자원 하나의 줄 맨 앞을 찾는 질의가 이 인덱스를 탄다.
CREATE INDEX landing_queue_resource_by_name
  ON landing_queue_resource(resource, row_id);

-- 기존 줄 행은 전부 랜딩 줄이다.
INSERT INTO landing_queue_resource(row_id, resource)
  SELECT id, 'landing' FROM landing_queue;
```

★ **`landing_queue` 를 `ALTER` 하지 않는다.** `resource` 컬럼을 더하는 판도 가산으로
통과하지만(실측: `modernc.org/sqlite v1.55.0` 에서 `ADD COLUMN … DEFAULT 'landing' CHECK(…)`
가 통과하고 CHECK 도 실제로 건다), 컬럼 하나로는 자원 집합을 표현할 수 없다.
그리고 백필을 `UPDATE` 로 하면 파괴적 조작(`opUpdateSet`)으로 마이그레이션 가드에 걸리는데
(`store/migrate_guard_test.go:87·234`), `INSERT … SELECT` 는 그 정규식에 안 걸린다.
**표를 더하는 쪽이 가드를 더 깨끗하게 통과한다.**

★ **기존 부분 유니크 인덱스를 그대로 둔다:**
`landing_queue_one_live_per_session(project, session_id) WHERE left_at IS NULL`.
그래서 한 세션은 **자원과 무관하게** 살아 있는 줄 행을 하나만 갖는다 —
"자원 A 를 쥔 채 자원 B 를 기다린다"가 성립하지 않으므로 순환대기의 전제가 사라진다.
다만 제약 4 대로 이것은 **스키마 보장이 아니라 불변식**이다: 그 불변식의 이름은 이미
`lane.divergent` 이고, 그것을 무는 시험을 §9 에 둔다.

**두지 않는 것과 그 이유**

- **`granted_at` 없음.** "내가 쥐었나"는 `HeldBy(project, resource)` 로만 파생한다.
  배타의 정본은 `resource_hold` 의 부분 유니크 인덱스이고 사본을 두면 갈릴 자리가 생긴다.
- **`priority` 없음.** 결정 표 참조.
- **자원별 `left_at` 없음.** 줄 행이 닫히면 그 행의 자원 전부가 함께 빠진다.
  all-or-nothing 이라 부분 이탈이 없다.

### 2. 취득 — all-or-nothing, 한 트랜잭션 안에서

DSN 이 `_txlock=immediate` 라 `land` 트랜잭션끼리 직렬화된다.

**`land(resources: ["landing"] | ["path:a.go","path:b.go"] | …)`** — 인자를 안 주면 `["landing"]`.

1. 내 살아 있는 줄 행이 없으면 → 줄 행 INSERT + 자원 INSERT.
2. 있으면 그 행의 자원 집합을 읽어 **요청 집합과 대조한다.**
   - 같으면 그대로 진행(재진입 안전 — 순번과 대기 시작 시각을 그대로 낸다).
   - **다르면 거절한다**: "너는 이미 자원 {…} 로 줄에 서 있다. 집합을 바꾸려면
     `land(leave:"사유")` 로 빠진 뒤 다시 서라."
     ★ 이것이 제약 4 의 `EnqueueLanding` 재진입 결함을 닫는 자리다. 지금은 다른 자원의
     줄 행을 성공으로 돌려주고, 그 뒤 `front(자원B)` 와 `mine(자원A 행)` 을 비교한다.
3. 내 행의 **모든** 자원 `r` 에 대해
   `frontLandingRowFor(project, r).ID == mine.ID` 이고 `HeldBy(project, r)` 가 비었으면
   → 전부 `AcquireResource` → **"네 차례다"**
4. 아니면 → **"너는 자원 `r` 에서 N번째"** — 막고 있는 자원 전부와 각각의 점유자·획득 경과·
   **점유자의 마지막 신호 나이**를 낸다.

`frontLandingRowFor` 는 `frontLandingRow` 를 대체한다:

```sql
SELECT q.id, q.session_id, q.enqueued_at
  FROM landing_queue q
  JOIN landing_queue_resource r ON r.row_id = q.id
 WHERE q.project = ? AND r.resource = ? AND q.left_at IS NULL
 ORDER BY q.id LIMIT 1
```

★ **순서 집행 지점은 여전히 하나다** — 3번의 비교. 다만 이제 **자원마다** 돈다.
이 조건이 없으면 순번은 표시용이 되고 "순서 큐"라는 이름이 거짓이 된다.

★ **굶주림이 없는 이유를 여기 적는다.** 자원 `r` 에서 내가 최선두가 되면 `r` 은 나보다 뒤
줄 행에게 나가지 않는다(3번이 그것을 막는다). 그래서 여러 자원을 요구한 줄 행도 자원들을
하나씩 "모으다가" 결국 전부 최선두가 된다. 이것이 보수적 2단계 잠금의 큐 형태이고,
부분 취득을 안 하므로 잡은 채 기다리는 구간이 없다.

**반납·이탈·회수**

- `land(result:"ok"|"fail", detail:…)` — 내 행의 자원 **전부** 반납 + 줄 행 닫기(같은 tx).
  점유자가 내가 아니면 "네 레인은 〈사유〉로 회수됐다"로 답한다(줄 행은 이미 `force` 로 닫혀 있다).
- `land(leave:"사유")` — 줄 행을 닫는다. **자원 미보유여도 성립한다.**
- `ReleaseLaneRow(rowID, reason)` — 그 행의 자원 **전부** `ForceReleaseResource` + 행 닫기.
  지금 `LaneResource` 하드코딩(`landing.go:577·584`)을 **행의 자원 집합**으로 바꾼다.
- `Service.Finish` — 손대지 않는다. `ListHeld` 로 자기 것을 전부 반납하고
  `CloseLandingRowBySession` 로 줄 행을 닫는데(`finish.go:461-526`) **이미 자원 무관**이라
  일반화 뒤에도 그대로 옳다.

**회수 판단 본문**(`laneReleaseBody`, `landing.go:601·713-717`)은 "그때 줄에 있던 사람"을
**그 행의 자원에 걸린 줄만** 적는다. 지금처럼 project 전체를 적으면 불변 기록에 다른 자원의
대기자가 박힌다 — 같은 파일 `:525-527` 이 금지하는 부류다.

### 3. `fd lane wait` — 폴링이되 대기 시간이 아니라 변화에 비례하게

```
fd lane wait [--resource <이름>]… [--timeout 9m] [--stale 30m] [--interval 2s]
```

- 읽기 전용 조회 `GET /api/v1/landing/queue?project=…` 를 **백오프**로 친다
  (2s → ×1.5 → 상한 10s). 줄이 바뀌면 간격을 2s 로 되돌린다.
- 조회 결과가 "내가 모든 자원의 최선두이고 전부 비었다"로 보이면 그때만 `land`(POST)를 쳐서
  **실제로** 취득한다. 취득의 정본은 여전히 §2 의 트랜잭션 하나다.
- 줄 상태가 바뀔 때마다 그 사실을 한 줄로 낸다("2번째 → 1번째", "앞사람 신호 3분 전").

★ **읽기가 `event` 를 안 남긴다.** 지금 `land` 는 시도마다 `t.LogEvent("lane.land", …)` 를
남기고(`service/landing.go:124`) 그 주석이 스스로 "대기 폴링의 비용을 못 본다"고 적는다.
`event` 는 추가 전용이고 정리 기구가 없다(`schema.sql:377`). 조회로 폴링하고 취득에만
쓰기를 쓰면 원장 증식이 **대기 시간이 아니라 실제 취득 횟수**에 비례한다.

★ **캐시를 안 탄다.** `Client.Read` 는 성공한 GET 을 **조건 없이** 캐시하고 미도달이면
조건 없이 꺼낸다(`client.go:241-243`). 그 경로로 폴링하면 서버가 죽은 뒤 30분 전의 줄 상태가
재생된다. `Healthz`(`client.go:312-315`)가 같은 이유로 `c.do` 직행에 캐시를 안 쓰는 선례다 —
`client.go` **안**의 메서드로 두면 `a.cli.do` 리시버를 보는 AST 관문에도 안 걸린다.

**종료**

| 갈래 | 출력 | 종료코드 |
|---|---|---|
| 차례를 잡았다 | "네 차례다(행 #N · 자원 …)" | 0 |
| `--timeout` 도달 | "아직 자원 r 에서 N번째다 — `fd lane wait` 를 다시 불러라" | 1 |
| `--stale` 도달 | "자원 r 의 〈점유자|앞 줄 행〉이 N분 무신호다. **자동 회수는 없다** — 사람이 판정한다: `fd lane release --row <행> --reason "…"`" | 1 |

★ **`--stale` 의 판정 대상은 "나를 막고 있는 것"이지 점유자만이 아니다.** 나를 막는 것은
두 종류다 — (a) 그 자원을 쥔 세션, (b) 점유는 없지만 나보다 앞 줄 행. **둘 다 본다.**
점유자만 보면 "아무도 안 쥐었는데 앞의 죽은 줄 행이 영원히 막는" 경우가 임계에 안 걸린다 —
회수 대상이 레인이 아니라 **줄 행**인 이유가 정확히 그것이다(원설계 §3).
막는 것이 여럿이면 **가장 오래 무신호인 것**을 낸다. 나이는 숫자로만 내고 死 판정은 안 한다.
| 줄 행이 회수됐다 | "네 줄 행은 〈사유〉로 회수됐다" | 1 |

★ 종료코드는 **기존 `LandExitCode` 규약을 그대로 따른다**(`cmd/fd/cmds.go:644-653` —
turn·released·left → 0, waiting 포함 나머지 → 1). 같은 상태를 `fd land` 는 1 로 내는데
`fd lane wait` 만 0 으로 내면 두 표면이 같은 사실에 다른 코드를 붙인다.

★ **`--background` 플래그를 안 만든다.** 대기를 길게 두고 다른 일을 하려면 부르는 쪽이
백그라운드로 띄운다(하네스 `run_in_background`: 프로세스가 끝나면 세션을 다시 부른다).
fd 가 데몬화하면 그 프로세스의 수명·정리·중복 실행이 전부 새 문제가 된다.

### 4. Stop 훅 — 라이프사이클 관문

`hookOutput` 에 계약 필드를 더한다:

```go
type hookOutput struct {
    HookSpecificOutput *hookSpecific `json:"hookSpecificOutput,omitempty"`
    Decision           string        `json:"decision,omitempty"` // "block" 또는 빈 값
    Reason             string        `json:"reason,omitempty"`
}
```

★ **`decision` 을 낼 조건은 `p.StopHookActive == false` 다 — 기존 가드를 그대로 쓴다.**
그러면 block 이 만든 턴의 끝에서는 **절대** block 이 안 나가므로 무한 루프가 원리적으로
불가능하다. 2026-08-04 실측(CC 2.1.221)의 기구는 "주입이 모델을 다시 부르고, 그 턴 끝에
또 주입한다"였고(`hook.go:518-523`), 이 가드가 그 사슬을 끊는 자리다.

★ **억제표(`(세션×키) 당 1회`)를 루프 방벽으로 쓰지 않는다.** `hook.go:525-533` 이
"그것은 우연한 edge-triggering이라 뚫린다"고 명시로 기각한 방벽이다. 그리고 억제표를 쓰면
block 이 줄 행당 1회로 묶여 **목적 자체를 못 이룬다.** 이 설계에서 지속을 담당하는 것은
`fd lane wait` 이고, block 은 "사람이 몰던 턴의 끝마다 한 번" 뜬다 — 처방과 같은 의미론이다.

**판정은 대화 단위다**(제약 2). 서버에 읽기 하나를 더한다: 대화(machine + cc_session_id)에
속한 카드 전부에 대해 살아 있는 선점·살아 있는 줄 행·자원 점유를 모은다.
`AckReach` 가 이미 그 단위로 세는 선례다(`prescribe.go:446-450`).

**단계와 문구** (위에서부터 먼저 맞는 것 하나만 낸다)

| 조건 | block reason |
|---|---|
| 살아 있는 줄 행이 있는데 그 행의 자원을 하나도 안 쥐었다 | "자원 〈r〉 줄 N번째다. `fd lane wait` 로 이어라 — 지금 턴을 끝내면 차례가 와도 못 받는다" |
| 살아 있는 선점이 있고 그 항목이 아직 안 닫혔다 | "선점 중인 항목 〈id〉 가 열려 있다. `finish` 로 닫아라" |
| 이 대화가 항목을 done 으로 닫았는데 `land` 를 한 번도 안 불렀다 | "〈id〉 를 닫았는데 랜딩 줄에 선 기록이 없다. `land` 로 줄을 서라" |

셋 다 아니면 **아무것도 안 낸다**(처방은 지금처럼 `additionalContext` 로 나간다).

★ **셋째 단계의 관측 구간을 못박는다: 이 대화의 카드들이 열린 뒤(`session.opened_at` 하한)
부터 지금까지.** 전 역사를 보면 이전에 랜딩까지 끝낸 항목이 매번 다시 걸리고, 이번 턴만 보면
finish 와 land 가 다른 턴에 있을 때(정상 순서다) 매번 걸린다. 억제표(`emittedKeys`)가 이미
같은 하한을 쓴다. 그리고 이 판정은 **`outcome='done'` 에만 건다** — `dropped` 는 랜딩할 것이
없다.

★ **셋째 단계는 "랜딩했나"가 아니라 "줄에 섰나"를 묻는다.** 실제로 머지·푸시가 됐는지는
서버가 git 을 읽어야 알고, 그 답은 워크트리마다 갈리며 `gitreader` 는 fetch 를 안 해
로컬 tip 만 본다(`gitreader.go:9-10`). 못 재는 것을 재는 척하지 않는다 —
줄에 선 기록(`landing_queue`)은 원장에 있고 그것만 묻는다.

★ **레인을 쥔 채 턴을 끝내는 것은 block 하지 않는다** — 랜딩 중 사람과 상의하는 정당한
경우와 구분할 수 없다. 대신 `additionalContext` 로 "레인을 쥔 채 턴이 끝났다 · 뒤에 N명"을
알린다. 붙들면 뒤에 선 세션 전원이 선다는 사실은 숫자로만 낸다.

★ **fail-close 규율은 그대로다.** 페이로드 해석 실패면 `hookStop` 이 그 자리에서 반환하므로
block 도 안 나간다(`hook.go:534-539`). 그 갈래에서 이 관문의 보장이 사라진다는 것은
받아들이는 대가이고, 반대(모르는 채 막기)는 세션을 못 쓰게 만든다.

★ **Stop 훅 타임아웃은 3초다.** 판정 읽기는 조회 하나여야 한다 — 훅 안에서 기다리는 설계는
애초에 불가능하다.

### 5. 랜딩의 문 — 항상 읽히는 자리와 거절 문구

**① MCP `instructions`** — `land` 라는 낱말이 없어서 아무도 줄에 안 섰다.

```
작업은 `pick`, 판단은 `note`, 끝나면 `finish`, 랜딩 전에 `land` 로 줄을 선다. 락은 없다.
```

3줄·300자 상한 안이다(`mcpsrv/protocol.go:32 InstructionsLimit = 300`).

## 시험 — 무엇을 잠그나

**취득과 순서 (store · service)**

- 서로 다른 자원을 요구한 두 세션 → **둘 다 취득한다**(자원별로 갈린다)
- 세션 A 가 `{r1}` 을 쥔 상태에서 B 가 `{r1,r2}` 요구 → B 는 **r2 도 안 잡는다**(all-or-nothing)
- 그 상태에서 C 가 `{r2}` 요구 → **C 도 못 잡는다**(B 가 r2 의 최선두라 뒤로 안 밀린다 = 굶주림 없음)
- A 가 빠지면 B 가 `{r1,r2}` 를 **한 번에** 잡는다
- 같은 세션이 **다른 자원 집합**으로 다시 서면 → **거절**(제약 4 의 재진입 결함)
- 같은 집합으로 다시 서면 → 순번과 대기 시작 시각이 **그대로**다
- 자원 `r2` 줄 행을 회수해도 `landing` 점유는 **안 건드린다**
- 회수 판단 본문의 "그때 줄에 있던 사람"에 **다른 자원의 대기자가 안 섞인다**
- 살아 있는 자원 점유가 있으면 반드시 대응하는 살아 있는 줄 행이 있다(`lane.divergent` 불변식)

**대기 (cmd/fd)**

- `fd lane wait` 가 **차례가 아니면 `land`(POST)를 안 친다** — 조회만 돈다
- 취득 성공 → 종료코드 0, `--timeout`·`--stale` 도달 → 1
- 오프라인에서 줄 조회와 취득이 **각각 다른 사유로** 거절되고 **아웃박스에 안 샌다**
- 폴링 경로가 `Client.Read` 캐시를 **안 탄다**

**훅 (cmd/fd)**

- `stop_hook_active=true` 면 **block 을 절대 안 낸다**
- 페이로드 파싱 실패면 block 도 `additionalContext` 도 안 낸다(fail-close 유지)
- 세 단계 각각에서 block reason 이 그 단계를 가리킨다
- 카드가 갈린 대화에서도 판정이 **대화 단위**라 줄 행을 찾는다
- 레인을 쥔 채 턴이 끝나면 block 이 **아니라** `additionalContext` 다

**표면**

- `instructions` 가 300자 이내이고 `land` 를 포함한다
- `land` 거절 경로가 규율 문구를 나른다(성공 응답이 아니라)

**만료 통지형**

- `landing_queue_resource` 를 읽는 프로덕션 호출자가 0이 되면 빨개지는 시험
- R=1.30·2.00 에서 추가 행동 요구 줄이 안 붙는다(§8)

## 범위 밖 — 일부러 안 하는 것

- **`.flightdeck.yaml` 의 `resources:` 를 안 읽는다.** 자원 이름은 첫 취득이 만든다.
- **우선순위 축을 안 만든다.** FIFO 다.
- **자동 만료·자동 회수를 안 만든다.** 나이는 숫자로만 낸다.
- **세션 死 판정을 안 만든다.**
- **"이번 세션의 R"을 안 만든다.** 제약 5 — 세션 몫은 `Delta()` 다.
- **`finish` 를 랜딩 여부로 거절하지 않는다.** 문서만 고친 작업·드롭·남이 대신 랜딩한
  경우가 전부 정당한데, 그 예외를 구문으로 만들면 이 항목보다 커진다. 강제는 Stop 훅 block 이다.
- **후속 생성 관문을 안 만든다.** "후속을 만들지 말라"는 이 세션의 운용 지시이고,
  서버 관문으로 만들면 R 을 낮추려 결함을 안 적는 굿하트가 된다(실물 1건).
  경로 경합으로 미루던 것은 `path:<경로>` 자원으로 줄을 서서 그 자리에서 처리한다.
- **`job` 표를 안 건드린다.** 자원 점유자는 세션만이다.
