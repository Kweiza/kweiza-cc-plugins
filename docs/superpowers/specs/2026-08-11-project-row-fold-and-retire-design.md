프로젝트가 생기는 자리는 하나다: `service/session.go:159` 가 세션을 열 때 없는 프로젝트를

## 3. 저장 자리 — 컬럼 둘, upsert 에는 안 넣는다

마이그레이션 007 이 `project` 에 둘을 더한다.

```sql
ALTER TABLE project ADD COLUMN pinned_at   TEXT;  -- NULL = 핀 아님
ALTER TABLE project ADD COLUMN archived_at TEXT;  -- NULL = 보관 아님
```

불리언이 아니라 시각인 이유는 `created_at` 과 같다 — **언제 접었는지가 없으면 되짚을 수 없다.**
보관 목록이 「언제 보관했는지」와 「그 뒤에 세션이 열렸는지」를 견주려면 시각이 있어야 한다.

★ **`UpsertProject` 의 `ON CONFLICT DO UPDATE` 목록에 둘 다 안 넣는다.** 그 upsert 는
`session.go:172` 에서 **세션이 열릴 때마다** 돌기 때문에, 넣으면 훅이 세션을 열 때마다 핀이
날아간다. `created_at` 이 이미 같은 이유로 그 목록 밖에 있어 선례가 있고, 그 자리의 주석
(「재등록이 나이를 0으로 되돌리면…」)에 이 두 컬럼의 근거를 같은 어법으로 잇는다.

`projectCols` 에 두 컬럼을 더하고 `model.Project` 에 `PinnedAt`·`ArchivedAt`(`time.Time`,
제로값 = 아님)을 더한다. **컬럼 목록과 `Scan` 순서를 함께 고친다** — 그 상수의 주석이
경고하는 실패(순서가 어긋나면 전부 문자열이라 타입 오류 없이 조용히 엉뚱한 값이 들어간다)가
컬럼을 더할 때 정확히 발생하는 부류다.

**핀은 전역이다.** 이 서버는 토큰 하나로 들어오는 한 사람의 판이라 사용자별 축을 안 만든다.

## 4. 화면

### 4.1 줄의 모양

```
프로젝트: kweiza-cc-plugins ★  context-platform ★   ▸ 나머지 9 (보관 3 포함)
```

펼치면 보통 6건이 ☆ 와 「보관」을 달고 나오고, 보관 3건은 그 아래 회색 줄에
**마지막 세션 시각과 함께** 나온다 — 되돌리는 길이 화면에 남고, 보관해 둔 것이 다시
돌기 시작하면 그 사실이 보인다.

**보관은 자동으로 안 풀린다.** 보관 뒤에 세션이 열려도 그대로 접혀 있다. 자동 해제를 넣으면
훅이 연 세션 하나로 `machine-probe` 같은 것이 다시 튀어나온다 — 그것이 애초에 이 항목이
생긴 이유다. 대신 화면이 마지막 세션 시각을 내고, 푸는 것은 사람이 한다.

### 4.2 규율 넷

- **핀이 0이면 지금처럼 전부 편다.** 그리고 줄이 「핀이 없다 — ★ 로 남길 것을 고르라」고
  말한다. 핀이 없다는 사실을 자동 판정으로 덮지 않는다.
- **접은 수를 항상 말한다.** §웹UI 가 `OutOfWindow`·`Folded` 에 이미 건 규율과 같은 것이다 —
  몇 건인지를 감추면 「없다」와 「접혀 있다」가 구분되지 않는다.
- **지금 보고 있는 프로젝트는 핀이 아니어도 줄에 보인다.** 안 그러면 화면이 자기가 어디
  있는지를 안 말한다. 이때 그 자리에 「이 프로젝트는 핀이 아니다」가 보이게 ☆ 를 함께 낸다.
- **보관된 것도 URL 로 그대로 열린다.** 보관은 목록에서 빼는 것이지 접근을 막는 것이 아니다.
  이것이 이 축을 표시 계층이라 부를 수 있는 근거고, §4.4 의 락 판정이 그 위에 선다.

### 4.3 `<details>` 다 — JS 는 0줄

기존 `.fold`/`.more`(`dashboard.gohtml:436`)는 **JS 로 접는다.** 스크립트가 없으면 전부
펴진 채로 남는 설계고, 긴 목록에는 그것이 옳다 — 폴백이 「다 보인다」이기 때문이다.

프로젝트 줄은 반대다. 스크립트가 없어도 **접혀 있어야** 요청이 성립한다. 그래서 `<details>`
하나로 간다. HTML 만으로 열리고 닫히며 이 페이지에 JS 를 한 줄도 안 더한다.

### 4.4 폼은 하나만 는다 — 그리고 락에 답을 적는다

새 라우트 하나: `POST /actions/project-view`. `web.go:100` 의 「라우트는 넷뿐이다」 주석과
`h.mux` 등록을 함께 고친다.

폼은 **하나**다. 버튼 여럿을 한 폼에 담고 값으로 무엇을 할지 말한다:

```html
<form class="pview" method="post" action="actions/project-view?key={{.WriteKey "project-view"}}">
  <input type="hidden" name="project" value="{{.Project.ID}}">   <!-- 돌아올 자리 -->
  <button name="axis" value="pin:kweiza-cc-plugins">★</button>
  <button name="axis" value="unpin:context-platform">☆</button>
  <button name="axis" value="archive:machine-probe">보관</button>
  <button name="axis" value="unarchive:figma-agent">되돌리기</button>
</form>
```

**토글이 아니라 명시적 값이다.** `pin:` 과 `unpin:` 을 따로 두면 같은 요청을 두 번 보내도
결과가 같다 — 화면 쓰기가 타는 멱등 키(`withScreenWrite`)와 어긋나지 않는다. 토글로 두면
같은 키의 재전송이 상태를 뒤집어 멱등이 거짓말이 된다.

이 라우트는 `/actions/*` 아래라 기존 화면 쓰기 미들웨어를 그대로 탄다 — 멱등 키와
`Origin`/`Sec-Fetch-Site` 대조. **새 우회로를 안 만든다.**

판정은 `actions.go` 에 순수 함수 `JudgeProjectView` 로 둔다. **`ActionKind` 와 안 섞는다** —
그 셋은 사유를 요구하는 판정이고 이 축은 사유가 없다. 섞으면 `JudgeAction` 의 「사유가
없으면 거절」이 이 축 때문에 헐거워진다. 반환은 같은 어법의 `Verdict{OK, Reason}` 이고
**사유는 항상 채운다**(없는 프로젝트 · 형식 위반 · 알 수 없는 축이 같은 실패로 안 접히게).

**`render_test.go:433` 의 락은 로그아웃과 같은 방식으로 이 폼을 이름으로 뺀다.** 상한 넷은
그대로 남기고, 왜 빼는지를 그 자리에 적는다:

> 이 폼은 파생물에도 원장의 사실에도 쓰지 않는다. `pinned_at`/`archived_at` 은 **누가 무엇을
> 보느냐**만 정하고 항목·판단·선점·랜딩 어디에도 안 닿는다. 접힌 프로젝트도 URL 로 그대로
> 열린다 — 그것이 이 축이 표시 계층이라는 증거다. 로그아웃을 뺀 근거와 같은 부류이되
> 자리가 쿠키가 아니라 원장이라, **접근이 안 막힌다는 사실**이 그 자리를 대신한다.

그 폼도 로그아웃과 똑같이 **먼저 정확히 하나인지 확인하고** 뺀다 — 없거나 여럿이면 뒤의
뺄셈이 조용히 틀린 수를 통과시킨다.

★ 같은 자리의 주석 하나를 **정정한다**: 「폼은 넷이다 — Tier A 쓰기 셋 + 프로젝트 고르기 GET
하나」의 넷째는 실제로는 **§6 판단 검색의 GET 폼**이다(`dashboard.gohtml:402`). 프로젝트
고르기는 지금까지 `<a>` 링크였고 폼이 아니었다. 수는 맞고 이름이 틀렸다.

## 5. CLI — 진짜 삭제는 여기에만

```
fd project ls
fd project rm --project <id> --reason <사유>          # 세기만 한다
fd project rm --project <id> --reason <사유> --yes    # 실제로 지운다
```

- `ls` 는 상태(핀·보통·보관) · 항목 수 · 세션 수 · 마지막 세션 시각을 한 표로 낸다.
  **지우기 전에 무엇이 있는지 보는 길**이고, 화면 없이도 이 축을 읽는 유일한 길이다.
- `rm` 은 `--yes` 없이 부르면 **함께 지워질 것을 세어 보여주고 멈춘다**(세션 · 신호 · 발자국 ·
  판단 · 선점 · 이벤트). 세는 것과 지우는 것이 같은 명령인 이유는, 다른 명령으로 세면
  세고 나서 지우기 전에 바뀐 것을 못 보기 때문이다.
- **항목이 하나라도 있으면 `--yes` 가 있어도 거절한다.** 639항목짜리를 한 명령으로 날리는
  길을 안 만든다. 강제 플래그는 **안 만든다** — 정말 필요해지면 그때 만든다.
- 사유는 필수다. 화면의 보관과 달리 **되돌릴 수 없기 때문**이고, 그것이 §2 가 사유를 가른 축
  그대로다. 원장에 `event`(`project.remove`)로 남는다.

### 5.1 원장이 정한 제약 둘 — 설계가 아니라 스키마가 정했다

**⒜ 판단이 하나라도 있으면 못 지운다.** `judgment.project` 는 `project(id)` 를 참조하는 FK 이고
`judgment` 에는 `judgment_no_delete` 트리거가 있다(`schema.sql:260`) — 판단은 원리적으로 못
지운다. 그러면 FK 가 프로젝트 행을 붙잡으므로 삭제가 불가능하다. **이것은 우회하지 않는다.**
`PRAGMA foreign_keys=OFF` 도 트리거 드롭도 안 쓴다 — 잔해 몇 건 때문에 원장의 가장 강한
보증을 깨는 값이 아니다.

지금 원장의 실측이 이 제약을 정확히 가른다:

| 프로젝트 | 판단 | 지울 수 있나 |
|---|---|---|
| `console-screen-landing` · `t6-…` · `upload-staging-…` · `machine-probe` · `aaron` · `infra` · `figma-agent` | 0 | **된다** |
| `design-context-platform` (5) · `stt-meetings` (1) | 있다 | 안 된다 → 보관으로 간다 |
| `context-platform` · `kweiza-cc-plugins` | 1448 / 551 | 안 된다 (항목으로도 이미 거절) |

**치우려던 잔해 넷은 전부 판단 0이라 지울 수 있다.** 판단이 있는 둘은 화면의 보관이 받는다 —
두 처방이 각자 덮는 자리가 여기서 정확히 맞물린다.

**⒝ `event` 는 안 지운다. 그리고 안 지워도 된다.** `event.project` 는 컬럼일 뿐 FK 가 아니다
(`schema.sql:366` — `project TEXT,`). 프로젝트 행이 사라져도 이벤트는 그대로 남고 FK 도 안
운다. 그래서 **「이런 프로젝트가 있었고 언제 지워졌다」가 원장에 남는다.** 지우는 명령이
자기 흔적을 남길 수 있는 이유가 이것이다.

### 5.2 지우는 순서 — 목록을 코드에 두고 시험이 스키마와 대조한다

`project(id)` 를 참조하는 표는 **10개**다(`session` · `session_workspace` · `ref_state` ·
`change_set` · `item` · `judgment` · `snapshot` · `counter` · `resource_hold` · `job`).
그중 `judgment` 는 §5.1 ⒜ 로 0건이 전제고, 나머지 아홉을 자식부터 지운다.

FK 는 없지만 `project` 컬럼을 들고 있어 **고아가 되는** 표가 둘 더 있다 —
`item_dependents` · `pick_eval`. FK 가 안 우니 안 지워도 삭제는 성공하고, 그래서 더 위험하다.
목록에 함께 넣는다.

★ 순서를 주석으로만 두지 않는다. **`store` 시험이 `schema.sql` 을 정규식으로 훑어
`project(id)` 참조 표 전부가 그 목록에 있는지 대조한다.** 표가 하나 늘면 그 시험이 빨개진다 —
안 그러면 새 표가 조용히 고아 행을 남기고, 그 사실은 아무 화면에도 안 뜬다.

서버 쪽은 `internal/api/handlers_projects.go` 에 `GET /api/v1/projects` 와
`POST /api/v1/projects/{id}/remove` 를 둔다. `DELETE` 를 안 쓰는 이유는 이 API 의 다른 쓰기와
같은 모양(POST + 사유 + 멱등 키)을 유지하기 위해서다.

- ★ **`UpsertProject` 가 핀·보관을 안 지운다** — 핀을 켠 뒤 upsert 를 돌리고 다시 읽는다.
  이 시험이 없으면 §3 의 함정이 조용히 재발한다(세션 하나 열릴 때마다 핀이 날아간다).
- `ListProjects` 가 두 값을 제대로 채운다(컬럼 순서 어긋남을 잡는다).
- 프로젝트 삭제가 딸린 행들을 함께 지운다 · **항목이 있으면 거절** · **판단이 있으면 거절**.
- ★ **삭제 순서 목록이 스키마와 일치한다** — `schema.sql` 에서 `project(id)` 참조 표를
  정규식으로 뽑아 목록과 대조한다. 표가 늘면 빨개진다(§5.2).
- 삭제 뒤에도 그 프로젝트의 `event` 행이 남는다(§5.1 ⒝ 의 단정).

**web**
- 핀 0 이면 전부 펴지고 「핀이 없다」 문구가 난다.
- 핀 2 면 나머지가 `<details>` 안으로 가고 **접은 수와 보관 수가 문구에 난다**.
- 지금 보고 있는 프로젝트는 핀이 아니어도 줄에 있다.
- 보관된 프로젝트를 `?project=` 로 열면 그대로 열린다(접근 차단이 아니라는 단정).
- 폼 락 갱신 — `pview` 폼이 정확히 하나이고, 그것을 뺀 수가 넷 이하 · POST 셋 · 사유 셋.
- `JudgeProjectView` 순수 함수: 없는 프로젝트 · 알 수 없는 축 · 빈 값이 **서로 다른 사유**로
  거절된다.

**cmd/fd**
- `rm` 이 `--yes` 없이는 안 지우고 셈만 낸다.
- `rm` 이 항목 있는 프로젝트를 `--yes` 와 함께 줘도 거절한다.
- `rm` 이 사유 없이 거절한다.

## 7. 안 하는 것

- **자동 활동 판정** — §2 에서 기각했다.
- **사용자별 핀** — 서버가 한 사람의 판이다.
- **MCP·CLI 보드의 변경** — 거기엔 프로젝트 목록이 없다. `fd status` 는 프로젝트 하나를 본다.
- **워크트리가 부모 프로젝트로 안 접히는 근본 고침** — 별건으로 큐에 낸다. `session.go:159`
  가 세션을 열 때 프로젝트를 자동 등록하고, 클라이언트의 `ProjectIDFromPath`(`env.go:654`)가
  주 저장소 루트를 쓰는데도 잔해 3건이 생긴 경위가 안 밝혀졌다. 그 항목이 닫히기 전까지는
  **지운 프로젝트가 다시 생길 수 있다**는 것이 이 설계의 알려진 한계다.
- **보관의 자동 해제** — §4.1 에서 기각했다.
- **FK·트리거 우회** — 판단이 있는 프로젝트를 지우려고 `PRAGMA foreign_keys=OFF` 를 쓰거나
  `judgment_no_delete` 를 드롭하는 길. §5.1 ⒜ 에서 기각했다. 그 둘은 증분 가드의
  `neverExempt`(`DROP TABLE`·`DROP COLUMN`·`RENAME`)가 노리는 것과 같은 부류의 손실이다.
