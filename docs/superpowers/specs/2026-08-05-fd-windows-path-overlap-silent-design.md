# fd-windows-path-overlap-silent — 경로 좌표계 관문

큐 항목 `fd-windows-path-overlap-silent` 의 설계. 선행 `sha:ddddad3`(fd-setup).

## 1. 무엇이 문제인가

경로 겹침 축 — "누가 어느 경로를 만지나" — 이 도구의 존재 이유다.
그 축이 **잘못된 좌표계의 경로 앞에서 오류가 아니라 '겹침 없음'을 낸다.**

`judge.components` 는 `strings.Split(p, "/")` 로만 쪼갠다. 그래서
`internal\api\x.go` 는 성분 **1개**가 되고, git 이 주는 `internal/api/x.go`(성분 3개)와
`pathRelated` 에서 절대 안 겹친다.

결과가 오류라면 사람이 본다. 그런데 결과는 **정상 응답과 구분되지 않는 "겹침 없음"** 이다.
이 항목이 겨냥하는 것은 백슬래시 자체가 아니라 **그 침묵**이다.

## 2. 실측

### 2.1 이관 대상은 0건이다

항목 본문은 "슬래시로 통일하면 `session_footprint` 에 쌓인 행의 이관이 따라온다 —
코드만 고치는 문제가 아니다"라고 경고했다. DB(`~/.flightdeck/fd.db`)의 경로형 컬럼을 전수 조사했다:

| 테이블.컬럼 | 행 | 백슬래시 |
|---|---:|---:|
| `change_set.paths` | 57 | 0 |
| `footprint.path` | 298 | 0 |
| `item.paths` | 321 | 0 |
| `project.path` | 5 | 0 |
| `session.worktree` | 102 | 0 |
| `session_workspace.path` | 66 | 0 |
| **합** | **849** | **0** |

Windows 드라이브 문자 경로도 0건. **마이그레이션은 이 설계에 포함되지 않는다** —
이관할 데이터가 존재하지 않기 때문이다. 항목이 가정한 가장 큰 비용이 실측으로 사라졌다.

### 2.2 `filepath` 는 서버와 클라이언트에서 다르게 동작한다

`path/filepath` 의 동작은 **컴파일 대상 OS**가 정한다. 서버(Linux)와 클라이언트(MCP·훅)는
별개 바이너리이므로 같은 함수가 양쪽에서 다른 답을 낸다.

| 서버 | 클라이언트 | 무슨 일이 나나 |
|---|---|---|
| Linux | Windows 네이티브 | `session.go:65` 의 `!filepath.IsAbs("C:\…")` 가 **true** → 세션 등록이 거절된다. 시끄럽게 죽는다 |
| Windows | Windows | 등록 통과 → `RelPath` 가 `internal\api\x.go` → **§1 의 침묵** |
| Linux | WSL/Linux | 현 상태. 문제 없음 |

그리고 `fd setup` 은 Windows 네이티브 클라이언트를 거절한다(ddddad3 — 진입점 `bin/fd` 가 bash,
`.mcp.json` 에 OS 분기 필드가 없어 훅도 MCP 도 뜨지 않는다).

⇒ **Windows 를 경유하는 침묵 경로는 지금 닫혀 있다.**

### 2.3 그런데 침묵은 Windows 클라이언트 없이도 도달 가능하다

경로가 DB 로 들어가는 입구를 전수 추적했다:

| 입구 | 검사 | 행 |
|---|---|---:|
| 세션 worktree — `service.JudgeOpenSession` | `filepath.IsAbs` | 102 |
| workspace — `api.ValidateWorkspacePath` | `filepath.IsAbs` (치는 클라이언트 0건) | 66 |
| 발자국 — `api.NormalizeFootprints` → `service.RelPath` | **없음** | 298 |
| **항목 경로 — `add` → `handlers_items.go:94`** | **없음 — 아무 검증도 없다** | **321** |

`add` 는 임의 문자열을 그대로 `item.paths` 에 넣는다. §2.2 의 두 칸과 달리 여기엔
**클라이언트 OS 라는 관문이 아예 없다** — 사람이 무엇을 붙여넣든 들어간다. Linux 에서
작업하는 사람이 Windows 쪽 문서나 IDE 에서 경로를 복사해 오는 것으로 충분하다.
그러면 그 항목의 경로 축은 조용히 죽는다. **가장 큰 입구가 가장 무방비다.**

`components` 주석은 `..` 를 일부러 안 걷어낸다며 "등록 목록에 `..` 가 들어오는 것은 입력
오류이고, 조용히 정규화하면 그 오류가 안 보인다"라고 적어 뒀다. 오류를 보이게 하겠다는
의도는 있는데 **보이게 하는 자리가 코드에 없다.**

### 2.4 검증 수단

`.github/workflows` · `Makefile` · `justfile` · `Taskfile` 전부 없다. CI 0건.

## 3. 결정

### 3.1 지원 범위: Linux/WSL 만

Windows 네이티브 클라이언트도 서버도 지원하지 않는다. 이미 그런 상태이고, 그것을 명시적 결정으로 올린다.

이 결정의 따름정리: **이 항목의 목표는 지원하지 않는 환경을 살리는 것이 아니라,
그 환경이 조용히 죽는 것을 막는 것이다.** 통과시켜 반쯤 동작하게 만드는 선택지(백슬래시
정규화 수용)는 이 결정과 모순되므로 기각한다 — 겹침 축만 살아나고 worktree 판정·git 실행은
여전히 깨져서, 사용자가 "동작한다"고 믿은 채 다른 자리에서 틀린 답을 받는다. **더 나쁜 침묵이다.**

### 3.2 `judge.components` 는 고치지 않는다

항목 본문이 지목한 자리이지만 **일부러 남긴다.**

**POSIX 에서 백슬래시는 파일명에 쓸 수 있는 합법 문자다.** `a\b` 는 Linux 에서 성분 하나짜리
정상 파일명이다. 백슬래시를 구분자에 넣으면 그 파일이 `a/b` 와 겹친다고 **오탐**한다.
침묵 하나를 없애려고 오탐 하나를 만드는 거래이고, 이 도구에서 오탐은 침묵만큼 나쁘다.

대신 **입구에서 막는다**(§4.2). 그리고 이 결정을 주석과 시험으로 못박는다 —
남긴 이유가 코드에 없으면 다음 사람이 "여기 버그네" 하고 되돌린다.

### 3.3 크로스컴파일 검사는 넣지 않는다

항목은 `GOOS=windows go vet ./...` 를 미결로 남겼다. 그것은 **Windows 지원을 전제했을 때의
질문**이고, §3.1 이 그 전제를 지웠다. 지원하지 않는 대상의 빌드가 깨지는 것은 회귀가 아니다.
게다가 크로스컴파일은 이 결함을 **원리적으로 못 잡는다** — Windows 빌드는 지금도 통과한다
(ddddad3 에서 확인). 실제 안전망은 §5 의 순수 함수 표와 이음매 시험이다.

## 4. 설계

### 4.1 좌표계 판정 — 순수 함수

`internal/judge` 에 판정 하나를 더한다. 이 패키지의 규율대로 **불리언이 아니라 사유**를 낸다.

```go
// PathVerdict 는 경로 좌표계 판정 결과다. 사유는 항상 채운다.
type PathVerdict struct {
	OK     bool
	Reason string
}

func JudgePathCoordinate(p string) PathVerdict
```

거절하는 것 셋:

| 입력 형태 | 판정 근거 | 사유에 담는 것 |
|---|---|---|
| `C:\repo\x.go` | `^[A-Za-z]:[\\/]` | Windows 드라이브 절대경로다. 이 서버는 POSIX 좌표계만 받는다 — WSL 에서 `/mnt/c/…` 로 띄워라 |
| `\\server\share\x.go` | `^\\\\` | Windows UNC 경로다. (같은 안내) |
| `internal\api\x.go` | 백슬래시 포함 | 백슬래시가 들어 있다. Windows 경로라면 위와 같다. **정말 파일명에 백슬래시가 있다면 이 도구는 그 경로를 지원하지 않는다** |

마지막 줄은 숨기지 않는다. 이 거절은 §3.2 가 말한 합법 POSIX 파일명 하나를 실제로 막는다.
**지원하지 않는다고 말하는 것**이 이 항목이 없애려는 침묵의 반대이므로, 사유에 명시한다.

통과시키는 것: 상대경로(`item.paths` 는 저장소 상대가 정상이다) · 빈 문자열(호출부가 이미
따로 다룬다) · `..`(별개 축이다 — §6).

### 4.2 관문을 세우는 자리 셋 — 처리가 셋 다 다르다

| 자리 | 처리 | 이유 |
|---|---|---|
| `service.JudgeOpenSession` (worktree) | **거절** | 이미 거절하지만 `C:\repo` 에 "절대경로가 아니다"라고 답해 원인을 못 짚는다. 사유를 정확하게 바꾼다. 세션 정체가 틀리면 그 뒤 전부가 틀린다 |
| `add` (`item.paths`) | **거절** | 사람이 대화형으로 넣으므로 즉시 고칠 수 있다. 통과시키면 그 항목의 경로 축이 영영 죽는다 |
| 발자국 (`api.handleFootprints`, `service.Beat`) | **버리되 버린 것을 관측 가능하게 남긴다** | 훅이 자동으로 보낸다. 400 으로 죽이면 세션 생존 신호가 끊긴다 — 그것이 침묵보다 나쁘다 |

발자국만 통과시키는 것이 이 설계에서 유일하게 비대칭인 자리다. 근거는 **실패의 대가**다:
항목 등록 실패는 사람이 즉시 보고 고치지만, 훅 실패는 세션이 보드에서 사라지는 것으로 나타나고
그 인과를 아무도 못 짚는다.

"관측 가능하게"의 실현이 두 표면에서 갈린다 — 실측으로 정한 것이다:

- `POST /sessions/{id}/footprints` (`handleFootprints`) → **응답에 싣는다.** 이 표면은 명시적
  호출이고 응답을 사람이 읽는다.
- `POST /sessions/{id}/signals` (`service.Beat`) → **event 원장과 로그에 남긴다.** 응답에
  실으려면 `Beat` 의 시그니처를 바꿔야 하는데 호출처가 5곳이고 그중 `mcpsrv.go:395` 는 다른
  세션이 만지는 중이다. 그리고 이 표면의 응답은 훅이 삼켜 사람이 읽지 않는다 — 원장이 더 강한
  자리다(영구적이고 대시보드에서 보인다).

### 4.3 계약을 주석이 아니라 코드로

`service.RelPath` 의 출력에 `filepath.ToSlash` 를 붙인다. Linux 에서는 무연산이다.
값을 바꾸려는 것이 아니라 **"이 함수의 출력은 슬래시 좌표계"라는 계약을 코드에 두려는 것**이다.
계약이 주석에만 있으면 다음 사람이 깬다.

## 5. 시험

1. **`JudgePathCoordinate` 표 시험** — 드라이브 경로 · UNC · 백슬래시 포함 · 정상 상대경로 ·
   정상 절대경로 · 빈 문자열 · `..` 포함. 각 사유가 원인을 담는지 함께 단정한다
   (사유가 비면 이 설계의 목적이 사라진다).
2. **`components` 회귀 방지 시험** — `components("a\\b")` 가 성분 **1개**를 낸다는 것을
   **의도로** 단정한다. §3.2 의 결정을 되돌리는 변경이 시험을 깨게 만드는 것이 목적이다.
   시험 이름과 주석에 "일부러 그렇다"를 적는다.
3. **입구 셋의 이음매 시험** — 세션 등록 거절 · `add` 거절 · 발자국 부분 수용(버린 건수가
   응답에 실리는지). 판정 함수를 다시 구현하지 않고 실제 경로를 태운다.
4. **`RelPath` 출력 계약 시험** — 슬래시 좌표계임을 단정한다.

## 6. 일부러 안 하는 것

- **`judge.components` 수정** — §3.2. 되돌리지 마라. 시험 2가 그 자리를 지킨다.
- **마이그레이션** — §2.1. 이관 대상 0건.
- **크로스컴파일 검사·CI 신설** — §3.3. CI 신설은 별도 항목감이다(어느 시험을 어떤 게이트로
  걸 것인가를 전부 정해야 한다).
- **`..` 성분 거절** — `components` 주석이 지적한 실재하는 문제이지만 좌표계 축이 아니다.
  같은 관문에 얹기 쉬워 보이나, 상대경로 정책 전반(`item.paths` 가 어디 기준인가)을 함께
  정해야 하므로 이 항목에서 분리한다.
- **`ValidateWorkspacePath`** — 같은 결함이 있으나 **이 표면을 치는 클라이언트가 0건**이다
  (`handlers_session.go:152` 실측 주석). 죽은 표면을 고치는 것은 이 항목의 목적에 기여하지 않는다.
