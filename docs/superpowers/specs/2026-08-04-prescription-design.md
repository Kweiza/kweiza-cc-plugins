# 처방 — 사건이 남게 만드는 강제 지점 설계

작성 2026-08-04 · 상태 **승인됨**(브레인스토밍 2026-08-04)

## 문제

병렬 세션이 서로의 진행을 파악하는 축은 **사건**이다 — 남이 알아야 할 순간(경로 요청·막힘·결정)에만
뜨고 평소엔 조용하다. 그 축은 이미 있다: `note(kind='ask'|'blocked')` 다.

**그런데 안 남는다.** 이 머신에서 실측한 보드는 세션 19건이 살아 있는데 미확인 사건은 1건이다.
`note` 를 부르는 자동 강제 지점이 없기 때문이고, 이건 DESIGN §0 이 병목 4위로 이미 지목해 둔 것이다 —
**"자동 강제 지점이 사실상 둘뿐이고, 안 불렀다는 사실조차 안 남는다."**

원하는 것: 기계가 판정할 수 있는 순간에 **그 자리에서** 무엇을 남겨야 하는지가 나오고,
안 남겼다는 사실이 관측 가능해진다.

## 조사에서 나온 제약 (설계를 실제로 바꾼 것들)

### ① 읽는 쪽은 이미 돈다. 비어 있는 것은 쓰는 쪽 하나다

사건 배달 경로가 둘 다 살아 있고 실물로 확인됐다:

```
server/cmd/fd/hook.go:135    SessionStart  → 보드 + Asks/Blocked 를 additionalContext 로
server/cmd/fd/hook.go:195    UserPromptSubmit → "flightdeck 미확인:" 주입
server/internal/service/board.go:102,105   liveNotesOfKind(Blocked) · (Ask)
```

이 세션의 시작 화면에 실제로 `[ask] mcpbackend.go 와 mcpsrv/ 를 잡는다` 가 떴다.

**그래서 이 설계는 배달 기구를 만들지 않는다.** 발화 기구만 만든다.

### ② 겹침 자체는 이미 파생축이다 — 사건이 나르는 것은 의도다

경로 겹침은 `footprint ∪ change_set` 으로 서버가 계산하고 `pick` 이 이미 낸다(DESIGN §5).
저 ask 가 나르는 값은 겹침이 **아니라** "내가 이걸 잡겠다"는 커밋 전 의도이고,
그건 §5 가 파생 불가로 못박은 넷 중 하나다.

**그래서 문제는 "어떻게 파생하나"가 아니라 "어떻게 그 순간에 남게 만드나"다.**

### ③ `note(kind='now')` 는 쓸 수 있는데 안 보인다 — 거짓 초록이다

```
server/internal/mcpsrv/tools.go:93    enum 에 "now" 가 있다 — 세션이 쓸 수 있다
server/internal/model/types.go:76     JudgmentNow 상수
server/internal/service/board.go:171  보드는 Ask·Blocked 만 읽는다 — now 는 어디에도 안 나온다
```

`now` 를 생산하는 코드는 레거시 임포터(`internal/legacy/session.go:53,55,61`)뿐이다.
즉 세션이 `note(kind='now')` 를 부르면 **저장은 되고 아무에게도 안 보인다.**
DESIGN §11 이 경계한 거짓 초록의 정확한 모양이다.

### ④ `event` 가 처방 상태를 담는다 — 새 테이블 0

```
server/internal/store/schema.sql:350  event(at, project, session_id, kind, payload)
                              :359    INDEX event_by_session(session_id, at)
                              :362,367 UPDATE·DELETE 트리거로 추가 전용
```

`(세션 × 조건 × 대상)` 당 1회라는 억제 규칙에 필요한 것은 "이 키를 이미 냈나" 하나이고,
그건 `session_id` 인덱스 + `payload` 조회로 답이 나온다. **마이그레이션이 없다.**

그리고 §10 이 요구한 "알림 확인율"이 별도 계측 없이 같은 자리에서 나온다.

### ⑤ Stop 훅은 미검증이다

지금 훅은 4종이고 `Stop` 은 없다(`hooks/hooks.json`). DESIGN §13 이 "추측을 사실로 적지
않는다"고 못박았으므로 **이 설계는 Stop 이 된다고 가정하지 않는다.** 실측이 1단계이고
실패 시 경로가 스펙에 있다(§5).

### ⑥ 접기가 예산 순이라 사건이 먼저 잘릴 수 있다

```
server/internal/service/service.go:44   DefaultLiveWindow = 8 * time.Hour
server/internal/mcpsrv/render.go:27     BoardTokenBudget = 1200
server/internal/mcpsrv/render.go:219-245  목록 순서대로 담다가 예산을 넘으면 그 뒤를 접는다
```

접기 기준이 **관련성이 아니라 목록 위치**다. 그래서 열린 ask 가 붙은 카드가
조용한 카드보다 먼저 접힐 수 있다. 실측 화면에서 19건 중 9건이 접혔다.

**사건을 카드에 붙이는 것만으로는 이 축이 안 고쳐진다.** 접기 규칙을 함께 고친다.

## 설계

### 1. 처방은 새 개념이 아니다

DESIGN §6 에 이미 있다 — **"규율은 응답에 싣는다 — 필요할 때만, 그 자리에서."**
지금 그 자리는 둘뿐이다(`finish` 의 빈 body, `pick` 꼬리). 이 설계는 **그 자리를 넷 늘린다.**

세션이 외우는 어휘는 그대로 `note`·`add` 다. 새 도구를 배우지 않는다.

| | 전 | 후 |
|---|---|---|
| MCP 도구 | 6 | **6** |
| 스킬 | 3 | **3** |
| 훅 | 4 | **5** (`Stop`) |
| 테이블 | 12 | **12** |

### 2. 판정 — 순수 함수 하나 (`internal/judge/prescribe.go`)

DESIGN §12: 판정 로직은 시험이 부르는 순수 함수에 있어야 한다. `fd setup` 이 0.2.6 에서
잡은 모양과 같다 — 판정은 Go, 행동은 바깥.

```go
type PrescribeInput struct {
    Now          time.Time
    SessionID    string
    Claims       []ClaimView   // 선점 항목 + 각자의 선언 경로
    TurnPaths    []string      // 마지막 처방 이후 새로 만진 경로 (처방이 없었으면 세션 시작 이후)
    Others       []OtherView   // 살아 있는 남의 세션 + 발자국·선점 경로
    LastJudgment time.Time     // 이 세션의 마지막 판단 (제로값 = 없음)
    NewPaths     int           // 마지막 판단 이후 새로 만진 경로 수
    Emitted      map[string]time.Time // 이미 낸 키 → 낸 시각
}

type Prescription struct {
    Key    string // 억제 단위이자 전이 식별자
    Reason string // 왜 떴는가 — §12 의 공허한 단정 방지
    Text   string // 세션에게 낼 문구
}

func Prescribe(in PrescribeInput) []Prescription
```

`Reason` 은 시험이 단정하는 축이다. 결과만 찍고 왜인지 안 남기면 조건 하나가 조용히
죽어도 초록이 유지된다.

**`Emitted` 가 불리언이 아니라 시각인 이유**: 억제 해제 규칙(`silent` 은 판단 뒤 다시 뜬다)이
`Emitted[key]` 와 `LastJudgment` 의 대소 비교로 표현된다. 불리언으로 받으면 그 규칙이
서비스 계층으로 새어 나가고, 그러면 §12 가 금지한 "시험이 로직의 사본을 단정하는" 모양이 된다.

### 3. 발화 조건 넷 — 상태가 아니라 전이에서만 뜬다

**억제 규칙은 하나다: `(세션 × Key)` 당 평생 1회.** 조건이 지속되는 동안 다시 안 뜬다.

| 조건 | Key | 뜨는 순간 | 처방 |
|---|---|---|---|
| 남과 경로 겹침 | `overlap:<상대 세션 id>` | 새 겹침 **상대**가 생긴 순간 | `note(kind='ask')` |
| 선언 경로 밖 | `outside:<경로>` | 선언 밖 **새 경로**를 처음 건드린 순간 | `add` 또는 `note(kind='decision')` |
| 판단 0건 | `silent` | 임계를 **넘는** 순간 | `note(kind='decision')` |
| 선점 없이 편집 | `unclaimed` | 그 세션의 **첫 편집** | `pick` 또는 `note(kind='decision')` |

**`silent` 임계 — 계획 중 실측이 이 값을 바꿨다.**

```
internal/store/schema.sql:91-96   signal PRIMARY KEY (session_id, kind)
```

**신호 표는 종류별로 한 행이고 갱신된다 — `tool` 신호 "횟수"라는 값이 없다.**
표를 12개로 유지하기로 한 이상(§1) 횟수는 못 쓴다. 그래서 일한 양의 축을 **발자국 경로 수**로
잡는다. `footprint` 는 경로마다 행이고 `LastAt` 이 있어 "마지막 판단 이후 새로 만진 경로"가
그대로 나온다. 새 표도 새 쓰기도 없다.

> **마지막 판단 이후 새 경로 ≥ 12,
> 또는 (새 경로 ≥ 1 **그리고** 마지막 판단 후 60분 경과).**

**시간 팔에 "새 경로 ≥ 1"이 붙는 것이 핵심이다.** 순수 OR 로 쓰면 조사만 하는 세션이
60분마다 걸리는데, 그건 이 절이 아래에서 "조사만 하는 세션에는 넷 다 안 뜬다"고
적어둔 것과 정면으로 어긋난다. 앞 판의 문안이 실제로 그랬고, 계획을 쓰다 잡았다.

`note` 가 들어오면 `silent` 키는 해제되어 다시 뜰 수 있다 — **넷 중 유일하게 재발화한다.**
(그 외 셋은 대상이 바뀌면 키가 바뀌므로 재발화가 필요 없다.)

`unclaimed` 가 세션당 1회인 근거: 이 조건은 흔하다. 실측 보드의 다수 세션이 선점 없이 돈다.
매번 뜨면 DESIGN §4 가 고발한 실패 — "살아 있는 5건 중 3건에 경고가 붙어 판별력이 0" — 를 재현한다.

**조사만 하는 세션에는 넷 다 안 뜬다.** 편집이 없으면 `overlap`·`outside`·`unclaimed` 의
입력이 비고, `silent` 는 `tool` 신호가 안 쌓인다. DESIGN §5 가 "그 세션은 경로 축에서
아무도 안 막는다"고 적어둔 것과 같은 취급이다.

### 4. 상태 — `event` 재사용

- 발화: `kind='prescribe'`, `payload={key, reason}`
- 확인: `kind='prescribe_ack'`, `payload={keys[], judgment_id}`

**`note` 한 번이 그 시점 열린 처방 전부를 닫는다.** 처방 문구가 무엇을 쓸지 지정하므로
보통 note 하나가 그것을 덮는다. 어느 키들이 열려 있었는지는 ack payload 에 남는다.

**무시해도 닫힌다 — 재출력하지 않는다.** 엣지 트리거이기 때문이다.
대신 `prescribe` 는 있고 대응하는 `prescribe_ack` 가 없는 것이 지표가 된다.
이것이 §0 병목 4의 "안 불렀다는 사실조차 안 남는다"를 닫는 자리다.

**그래서 `silent` 은 확인하면 다시 뜨고 무시하면 영영 안 뜬다.** 모순처럼 읽히지만 의도한 것이다 —
판단을 남기는 세션은 다시 조용해졌을 때 한 번 더 찔러야 하고, 한 번 무시한 세션을 계속
찌르는 것은 §4 가 고발한 상시 점등이다. **재촉은 이 설계에 없다.**

**한 번에 내는 처방은 최대 3건이다.** 넘으면 상위 3건만 문구로 내고 나머지는
`외 N건(outside:… )` 한 줄로 요약한다. **키는 전부 발화 기록한다** — 요약된 것도 이미 낸 것이다.
대규모 리팩터 한 턴이 `outside:` 처방 40건을 쏟는 경로를 막는다.

### 5. 배달 — `Stop` 훅. 실측이 1단계다

```
POST /api/v1/sessions/{id}/prescriptions   →  {prescriptions: [...]}  + 발화 event 기록
```

**이 표면은 세션 카드 파생을 안 돈다.** DESIGN §6 이 `/notices` 를 `/dashboard.json` 에서
가른 것과 같은 이유다 — 매 턴 도는 경로에 `git worktree list` + 세션별 저장소 훑기를
얹으면 세션이 늘 때 **모든 턴 종료에 그 비용이 얹힌다.** 필요한 입력(`footprint`·`claim`·
`signal`·`judgment`)은 전부 DB 테이블이라 git 을 안 탄다.

훅은 `${CLAUDE_PLUGIN_ROOT}/bin/fd hook stop`, `async: false`, timeout 3초, **fail-open**.

#### 실측 항목 셋 — 이 머신에서 재고 DESIGN §13 에 적는다

1. `Stop` 훅 stdin 페이로드에 `session_id` 가 오나
2. stdout 이 다음 턴 컨텍스트로 주입되나 — `hookSpecificOutput.additionalContext` 형식인가 평문인가
3. `stop_hook_active` 재진입 동작

#### 실패 시 경로

주입이 안 되면 **`UserPromptSubmit` 채널로 떨어진다**(이미 도는 경로, 실측 불필요).
지연이 생긴다 — 사람이 말을 걸 때까지 안 뜬다. 그 사실을 숨기지 않는다.

**어느 채널로 나갔는지는 `fd doctor` 가 이름으로 낸다**(DESIGN §13: 부재를 기본값으로 접지 않는다).

### 6. 표면

REST 하나가 늘고 MCP 는 안 는다. CLI 는 `fd hook stop` 만 는다.

### 7. 읽기 — 사건을 카드에 붙인다

지금 `Asks`·`Blocked` 는 보드 **꼬리에 전역으로만** 나와서 누가 남겼는지가 카드와 안 이어진다.
렌더만 고친다(스키마 변경 0):

```
 01KZ5HKD… · 브랜치 ? · active · 경로 2: DESIGN.md, skills/fd-setup/SKILL.md
   tool 7분 · mcp 7분 | 선점 없음
   [ask 12분] mcpbackend.go 와 mcpsrv/ 를 잡는다
```

**꼬리의 전역 목록은 남긴다.** 카드가 접히면 사건도 접히기 때문이다 — 꼬리가 그 안전망이다.

### 8. 보드 노이즈 — 두 조각

#### (a) 접기를 관련성 순으로

예산이 자르는 것은 이 순서의 **뒤부터**다:

1. 나
2. 사건이 붙은 카드(열린 `ask`·`blocked`)
3. 나와 경로가 겹치는 카드
4. 나머지 — 마지막 신호 최신순

#### (b) 창을 8시간 → 2시간

**이 숫자에는 근거가 없다. 그 사실을 상수 주석과 이 스펙에 적는다.**
DESIGN §10 이 고발한 것이 정확히 이것이다 — "락 다섯 개 중 ttl 근거 주석이 있는 것이 하나뿐".
근거 없는 상수를 근거 있는 척 넣으면 같은 실패를 새 이름으로 재현한다.

**근거는 만들 수 있고, 그 재료가 이미 DB 에 있다.** `signal` 테이블로 "마지막 신호 후
다음 신호까지의 간격 분포"를 재면 "이 구간 이후엔 사실상 안 돌아온다"가 나온다.
그 실측은 이 스펙의 범위 밖이고 **큐 항목으로 남긴다**(`fd-live-window-baseline`).

**잘린 것을 침묵시키지 않는다.** DESIGN §4 는 "죽었다"고 쓰는 것을 금지한다 —
창은 표시 구간이지 생존 판정이 아니다. 그래서 한 줄이 반드시 남는다:

```
창 밖 9건(마지막 신호 3~7시간 전) — window=8h 로 본다
```

### 9. `now` 를 도구 enum 에서 뺀다

쓸 수 있는데 아무 데도 안 보이는 것은 거짓 초록이다(제약 ③).
`tools.go` 의 `note.kind` enum 에서 `"now"` 를 제거한다.
`model.JudgmentNow` 상수와 검증 목록은 **남긴다** — 레거시 임포터가 생산하고,
DB 에 이미 있는 행을 못 읽게 만들면 안 된다.

## 안 만드는 것

| 안 만든다 | 왜 |
|---|---|
| **후속 항목 자동 등록** | "후속이 생겼다"는 DESIGN §5 의 파생 불가 넷과 같은 성질이다. 기계가 못 잡는다. 대신 `outside:` 처방이 그 자리에서 `add` 를 처방한다 — **선언 경로 밖으로 나간 것이 기계가 잡을 수 있는 유일한 "이건 별개 작업이다" 신호다** |
| 진행률·단계 필드 | "사건만"이 선택됐다. 상태 필드를 만들면 그것이 또 하나의 손 기재가 되고, 갱신 안 된 단계는 조용히 거짓이 된다 |
| transcript 파싱 | DESIGN §13 의 확인된 플랫폼 사실 목록에 없다. 못 하는 것을 하는 척하지 않는다 |
| 새 MCP 도구 | 처방은 기존 `note`·`add`·`pick` 을 부르라고 말할 뿐이다 |
| 처방 재출력·에스컬레이션 | 상시 점등으로 가는 가장 짧은 길이다. 무시는 지표로만 남는다 |
| 생존 판정 | 창은 표시 구간이다. DESIGN §4 를 뒤집지 않는다 |

## 시험 규율 (DESIGN §12)

- `Prescribe` 조합 전수 — 조건 넷 × (이미 냄 / 안 냄) × (대상 바뀜 / 그대로).
  각 케이스가 `Reason` 을 단정한다.
- **단정은 소비자의 좌표계로.** 대상은 `fd hook stop` 의 **stdout 실물 문자열**이다.
- 접기 순서는 **렌더 출력 문자열**로 단정한다 — 사건 붙은 카드가 조용한 카드보다 앞에 있는가.
- 새 검사는 망가진 것을 넣어 **빨간불을 먼저 확인한다.**
- 통합: 서버를 죽인 상태에서 `Stop` 훅이 fail-open 하는가(조용히 성공, 세션을 안 막는다).

## 아직 모르는 것

1. `Stop` 훅 실측 셋(§5). **이 설계의 유일한 미검증 의존이다.**
2. 창 2시간의 근거 — 별도 항목(`fd-live-window-baseline`).
3. `silent` 임계 12경로/60분의 근거. 잠정값이고, 발화율이 실측되면 조정한다.
   창 2시간과 같은 성질의 미지수다 — **근거 없음을 상수 주석에 적는다.**

## 성공 지표와 반증 축

- **성공**: 세션당 사건 수 > 0 인 세션 비율. 지금 19건 중 1건이다.
- **반증**: `prescribe` 대비 `prescribe_ack` 비율이 떨어지면 처방이 소음이 됐다는 뜻이다.
  DESIGN §10 의 "알림 확인율"이 그대로 이 축이다. **떨어지면 조건을 줄인다, 문구를 키우지 않는다.**
- **경계**: 세션당 판단 바이트(§10). 처방이 짧은 형식적 note 를 유발하면 건수는 오르고
  바이트는 안 오른다. 둘을 함께 본다.
