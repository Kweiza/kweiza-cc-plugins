# finish 가 이미 있는 항목을 후속으로 **잇는다**

- 항목: `fd-finish-cannot-link-an-existing-item-as-followup`
- 날짜: 2026-08-06
- 경로: `internal/service/finish.go` · `internal/service/finish_followups.go` · `internal/service/finish_followups_test.go` · `internal/mcpsrv/render.go`(RenderFinish 만) · `internal/mcpsrv/tools.go`(followupSchema 만)

## 1. 항목의 전제 하나가 틀렸다 — 실측

항목 본문은 "`followups` 는 항목을 **새로 만든다**. 이미 있는 id 를 넣으면 같은 id 를 다시
만들려다 실패한다"라고 적었다. 실측으로 확인한 결과 **실패하지 않는다.**

탐침(임시 시험, `Finish` 에 남이 만든 항목 id 를 후속으로 넣음):

```
Followups=[] Skipped=[someone-elses]
남의 항목에 걸린 판단 1건 — [handoff]
항목 본문 그대로다(안 덮었다)
```

이유는 둘이다.

- `finish.go` ①이 판단 링크를 **`in.Followups` 전부**로 짠다 — 항목이 실제로 만들어졌는지
  보기 **전**이다. 그리고 `judgment_link.target_id` 에는 FK 가 없다(`schema.sql` 265행이
  "끊긴 포인터가 원리적으로 사라진다"는 이유로 일부러 안 걸었다). 그래서 존재하지 않거나
  남의 것인 id 로도 링크 행이 그냥 들어간다.
- ②의 `AddItem` 중복만 `ConflictDuplicate` 로 흡수되어 `SkippedFollowups` 에 실린다.

즉 **잇기는 이미 되고 있다. 다만 아무도 그렇게 말하지 않고, 아무도 그것을 검사하지 않는다.**

## 2. 그래서 진짜 결함은 둘이다

**① 표면이 거짓말을 한다.** `FollowupsGuidance` 는 "이미 add 로 만들어져 있어서 지금
followups 로 옮길 수 없다 … 대신 `note(kind='handoff', item_id=…)` 로 걸어 두라"라고 말하고,
`RenderFinish` 는 "후속 N건은 **안 넣었다**"라고 말한다. 둘 다 사실이 아니다. 그 말을 믿은
세션은 이미 걸린 링크 위에 `note` 로 중복 판단을 하나 더 만든다. 항목 본문이 인용한
`01KZ7V79ZXGJ4QRQ541W42F891` 이 바로 그 사례다.

**② 자격 검사가 없다.** 오타 하나로 **남의 항목**이 내 판단에 조용히 이어진다. 항목 본문이
"오타로 남의 항목을 자기 후속으로 삼는 사고"라고 우려한 그 문이 이미 열려 있고, 응답은
그것을 "안 넣었다"로만 말해 아무도 못 본다.

이 설계는 잇기를 **새로 만드는 것이 아니라, 이미 일어나던 일을 명시적·안전·정직하게**
만든다.

## 3. 정한 것

- **이을 자격은 "관문이 이름을 낸 것"뿐이다** — 이 세션이 **이 선점 뒤에** 만들었고 아직
  **열려 있는** 항목. `followupCandidates` 의 정의 그대로다. 관문이 "이것들을 후속으로
  넣어라"라고 부른 목록이 곧 "이을 수 있는 것"의 정의가 된다. 두 목록이 갈리면 다음 개정에서
  어긋난다.
- **부적격 id 는 그 자리에서 거절한다** — 남의 항목 · 이미 닫힌 항목 · 선점 전에 만든 항목.
  후속 검증 루프(제목·본문 없음, 경로 좌표)와 **같은 자리, 같은 모양**이다. 판단 본문은 아직
  세션 손에 있으니 그 후속만 빼고 다시 부르면 된다.
- **잇기는 `id` 만으로 한다** — 이미 있는 항목의 제목·본문을 다시 적게 하고 서버가 버리는
  것은 조용한 거짓이다. 도구 수도 인자도 안 늘린다(DESIGN §6).
- **링크는 트랜잭션 안에서 짠다** — 존재 확인과 삽입이 같은 트랜잭션에 있어야 경합 창이
  닫힌다. `finish.go` 가 `holds` 를 tx 안에서 읽는 것과 같은 근거다.

## 4. 구조

### 4.1 분류기 (`finish_followups.go`)

`followupCandidates` 를 둘로 가른다.

```
sessionSpawnedOpen(ctx, in) []string    // 이 선점 뒤 이 세션이 만든 열린 항목 전부
followupCandidates(ctx, in) []string    // 위에서 이번 호출에 실린 id 를 뺀 것 (기존 의미)
```

관문이 부르는 목록과 이을 수 있는 목록이 **한 정의**에서 나온다.

`classifyFollowups(ctx, in)` 이 followup 마다 셋으로 가른다:

| 상태 | 판정 |
|---|---|
| `sessionSpawnedOpen` 에 있다 | **잇기** |
| 없는데 그 id 의 항목이 이미 있다 | **거절** |
| 아무것도 없다 | **새로 만들기** |

거절 사유는 그 id 가 왜 부적격인지와 함께 **이을 수 있는 것의 이름을 전부** 낸다. 이름 없이
거절하면 세션이 무엇을 넣을지 다시 조사한다.

`sessionSpawnedOpen` 이 관측에 실패하면(선점 시각·이벤트 조회 실패) 빈 집합이다. 그러면
기존 id 는 전부 부적격이 되어 거절이 늘어난다 — 관문의 fail-open 과 방향이 반대다. **의도적이다**:
관문은 "안 막는 쪽"이 안전하지만(마무리를 잃지 않는다), 잇기는 "안 잇는 쪽"이 안전하다
(거짓 링크를 안 만든다). 거절 문구가 그 사실을 말한다.

### 4.2 `Finish` 의 순서 (`finish.go`)

1. `JudgeFinish`(기존)
2. `judgeMissingFollowups`(기존) — 잇기도 `in.Followups` 에 들어오므로 관문은 그대로 만족된다
3. `classifyFollowups` — 부적격이면 여기서 거절(tx 진입 전, 판단 미저장)
4. 검증 루프 — `title`·`body`·경로 좌표 관문은 **새로 만드는 것에만** 건다
5. tx:
   - 맨 앞에서 `t.GetItem` 으로 재확정하고 그 결과로만 링크 목록을 짠다
     - 잇기 대상이 사라졌거나 닫혔다 → 링크에서 빼고 `SkippedFollowups`(마무리는 안 잃는다)
     - 새로 만들 대상이 그 사이 생겼다 → 만들지도 링크하지도 않고 `SkippedFollowups`
   - ① `AddJudgment` — 링크 = 실제로 만들 것 + 실제로 이을 것
   - ② `AddItem` 은 **새로 만들 것만** 돈다. 기존 중복 흡수 갈래는 이제 도달 불가지만
     **지우지 않는다** — 그 전제(tx 안 읽기)에 달려 있다는 사실을 주석으로 남긴다.
     `lane.release_skipped` 갈래가 같은 형태의 선례다.
   - ③④(종료·반납)는 무변경

### 4.3 표면

- `FinishResult.LinkedFollowups []string` 추가. 원장에 `item.followup_linked` 이벤트
- `RenderFinish`: "기존 항목 N건을 후속으로 이었다: … (판단과 링크로 이어졌다)" 줄 추가.
  "후속 0건" 문구는 **등록과 잇기가 둘 다 0**일 때만 뜬다
- `FollowupsGuidance` 의 ★문단을 사실로 교체: 이 선점 뒤 만든 열린 항목이면 `followups` 에
  **id 만** 넣으면 이어진다
- `tools.go` `followupSchema`: 필수를 `id` 하나로 낮추고, "이미 있는 id 면 만들지 않고
  잇는다(이 세션이 이 선점 뒤 만든 열린 항목만)"를 적는다. `title`·`body` 설명에 "새로 만들
  때 필수"

## 5. 오류 처리

| 상황 | 결과 |
|---|---|
| 부적격 id(남의 것·닫힌 것·선점 전) | tx 전에 `RefusedError`. **판단은 저장 안 된다** |
| 새 항목에 `title`·`body` 없음 | 기존과 같이 거절 |
| 잇기 대상이 tx 사이에 사라짐 | `SkippedFollowups`, 마무리는 성공 |
| 관측 실패(선점 시각·이벤트) | 자격 집합이 비어 기존 id 는 거절된다(안 잇는 쪽으로 닫힌다) |

## 6. 시험 (TDD — 빨강 먼저)

1. **회귀**: 부적격 id 를 주면 그 항목에 판단 링크가 **안 걸린다** — 오늘의 결함을 고정한다
2. 잇기 성공: 선점 뒤 만든 항목을 `id` 만으로 후속 → 항목 본문 무변경 · 링크 존재 ·
   `LinkedFollowups` 에 이름 · 같은 호출에서 관문이 안 울린다
3. 부적격 셋(남의 것 · 닫힌 것 · 선점 전) 각각 거절 + **판단이 저장 안 됐다**
4. 새 항목은 여전히 `title`·`body` 필수
5. 렌더: 잇기 줄이 나오고, 등록·잇기가 둘 다 0일 때만 "후속 0건"이 나온다

## 7. 일부러 안 하는 것

- **`link_followups` 같은 별도 인자.** 항목 본문이 기각 후보로 적었고 DESIGN §6 예산에 걸린다.
- **②를 ① 앞으로 옮기기.** 링크가 정의상 결과가 되어 더 정직하지만, "판단을 가장 먼저
  저장한다"는 서사와 그 근거 주석을 뒤집어야 한다. tx 안 읽기로 같은 정확성을 얻는다.
- **`SkippedFollowups` 표면 제거.** 도달 경로가 좁아지지만 tx 내 경합 갈래가 아직 그것을 쓴다.
- **기존 `note(item_id=…)` 우회 차단.** 그 길은 여전히 옳다(이 선점과 무관한 항목에 판단을
  걸 때). 문구에서 "잇기가 불가능하다"는 거짓만 걷어낸다.
